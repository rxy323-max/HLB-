# CRA 放款 / STP 放款 / OCR — 需求梳理

> 本文在 `06_放款/README.md`（原始需求罗列）基础上，从业务角度重新梳理三者关系，并给出「放款案件比例图」需要向客户索取的前置数据清单。
> 关键修正见第 0 节。

---

## 0. 核心业务模型（对早期理解的修正）

**修正点：OCR 只承担「填入 / 反显」一个角色，它不替代复核。复核环节对所有放款案件都存在。**

早期把 OCR 分成「反显提效」和「免检替代人」两类，容易被误解为"STP 案件里 OCR 取代了 CRA"。实际业务流程是统一的一条主干：

```
                       ┌─────────── 放款方式（新车/二手/FBR…）作为输入
                       ↓
 Sales 上传/提交 →  OCR 分类·填入(反显)  →  CRA 复核(结果确认)  →  业务(专家)规则校验
                                                                        │
                                                      ┌─────────────────┴─────────────────┐
                                                      ↓                                   ↓
                                             CRA 人工处理                          STP 自动放款
                                        （全程人工维护+授权）              （自动执行放款/建户/文书/邮件）
                                                      └──────────────┬────────────────────┘
                                                                     ↓
                                                                   生效
```

- **OCR = 填入**：把文件字段抽出来，反显/回填到放款维护页面，减少人工录入。无论案件最终走人工还是 STP，OCR 的角色都一样，只是"帮忙填"。
- **复核 = 始终存在**：只要过 STP 放款，业务流程上 OCR 作为填入，**仍由 CRA 复核**（对 OCR 结果做确认/交叉验证）。区别在于复核的形态——人工复核，或由「专家规则自动校验」把 CRA 的核对规则系统化执行。
- **STP 省掉的是「人工执行放款操作」**，不是复核。符合资格且规则通过的案子，系统自动完成 Host 维护、建户、打款、文书生成与邮件，无需 CRA 人工经手这些执行动作。

> 待与客户确认：放款主 FRS 对 STP 的定义原文是「Sales 提交到 CRA 后，funding 前无 CRA 人工介入」。本节按业务实况理解为「复核环节始终存在（人工或规则化），STP 自动化的是放款执行」。二者措辞需在评审时对齐口径。

## 1. CRA 放款需求梳理（人工主干）

CRA 放款是所有案件的**基础流程**，STP 是它之上的自动化增强。

### 角色
| 角色 | 职责 |
|------|------|
| Sales | 收齐材料上传、触发 E-Hakmilik 抵押登记、查 FIS/Dealer 资格、提交放款申请 |
| CRA Checker / Maintenance | OCR 结果确认、放款信息维护、缺陷(Defect)处理、专家规则未过案件的人工核对 |
| CRA Authorizer | 放款授权把关；授权限额=批准贷款额+手续费+GST/SST；不得与最近 checker/缺陷处理人同人（双人原则） |
| System / AIOCR + 专家规则 | 文件分类、字段提取、交叉验证、规则自动校验、（STP）自动放款 |

### 主流程段
1. **Sales 提交段**：E-Hakmilik 抵押登记 → FIS 查询（车辆登记状态 verified/processed）→ Dealer FBR/FBT 资格查询 → 上传文件 → 提交（触发 Host Acceptance：CIF/额度/抵押创建）
2. **系统预处理**：文件分类 → 完整性校验 → OCR 提取 → 交叉验证
3. **预分流**：OCR 交叉验证通过 + 自动路由开关 ON → 专家规则自动校验；否则 → CRA Checker 人工队列
4. **专家规则校验**：14 类规则（详见 README §3.3 与 Appendix xlsx）；通过 → STP 决策；失败 → 人工队列 + 自动登记缺陷
5. **人工维护/授权**（非 STP 或开关 OFF）：Checker 维护 → Authorizer 授权
6. **放款执行**（人工与 STP 共用）：Host Maintenance → Account Creation → Disbursement 打款 → 文书生成（加密/非加密 PDF）→ 邮件外发；接口超时进 Error Queue
7. **收尾**：Full Maintenance 一次做完；非 Full Maintenance → Post Maintenance 补做
8. **放款后**：LHDN 电子印花税、RBS/eTracker 状态回传、对账/绩效报表

## 2. STP 放款需求梳理（自动化增强）

### 2.1 硬性资格（7 条，全满足才可进 STP；业务含义）
| 条件 | 为什么卡这条 |
|------|------|
| 1. 个人（Individual） | 公司/合伙涉及决议、授权签字人、多担保人、多语言文书，判断复杂，不能免人工执行 |
| 2. 新车（New car） | 二手/复新要验 VOC、payoff、车检、AP 进口证等大量额外材料，变量多 |
| 3. 唯一受益人且与 Dealer 系统一致 | "钱打给谁"必须无歧义；系统已交叉确认资金流向，无需人工核打款对象 |
| 4. 无清偿（No payoff） | 不涉及替客户结清旧贷，无需算结算金额、协调旧贷款行 |
| 5. 非 FBT | FBT=车未过户先放款，银行额外风险敞口，需人工核车商额度与担保 |
| 6. 无定存质押（No FD pledge） | 无需人工核 FD 金额/质押期限/LOSO 与批复一致性 |
| 7. 非 Floor Stock 车商 | 批发融资车商属高风险类别，放款需额外核车商整体敞口 |

### 2.2 时效硬闸（90 天三层级）
批复有保质期，超期风险状况可能变化，逐层兜底：
1. 当前日期 ≤ 首批日+90 天 → 放行；否则查 2
2. （FBR/FBT）注册日缺失→拦；注册日 ≤ 首批日+90 天 → 放行；否则查 3
3. LOU 展期日缺失→拦；当前日期 ≤ LOU 展期日+90 天 → 放行；否则拦

### 2.3 分流控制
- **STP 总开关 `STP_SWITCH`**（默认 OFF）：管理层的"一键刹车"。ON=符合资格的案子走自动放款；OFF=即使合格也降级回 CRA Authorizer 人工。用于上线初期或异常时的运营级风险控制。
- **Full Maintenance Indicator**：决定放款后收尾是否一次做完。
  - Yes：放款 → 文书生成 → 邮件外发 一次到底
  - No：只做到"放款"，状态置 `Funded Pending Post Maintenance`，转 **Post Maintenance** 队列由人工补做后续文书/账务（如 FBR/FBT 的 Appendix 须待完全放款/过户后才能生成）
- **Post Maintenance = 放款后维护环节**：专门处理不能在放款当场一次做完的后续动作。

### 2.4 STP 案件的数据打标
- 通过 STP 决策 → 记 `STP Application Indicator`（报表过滤用）
- 柜员 ID 记为 System teller ID（区别人工的 Authorizer ID）

## 3. OCR 需求梳理（修正后表述）

OCR 在放款阶段的**唯一定位是"字段填入/反显"**，服务于"减少人工录入、支撑规则校验"，不做决策、不替代复核。它带来的价值分两个层面（但底层是同一个 OCR 能力）：

| 层面 | 说明 | 对应流程 |
|------|------|---------|
| **A. 反显填入（提效）** | 抽取文件字段自动回填放款维护页，CRA 人员由"手工敲"变"目视核对+确认"（对应 `Business_Rule_Validation4.html` 的 Confirm/Error/Edit 工作台）；三色状态监控 OCR 进度 | 所有案件通用 |
| **B. 支撑规则自动校验（为免检铺路）** | OCR 交叉验证通过后，抽取结果喂给专家规则做全量自动核对；全过则该复核环节可由规则替代人工，案子具备走 STP 自动放款的前提 | STP 候选案件 |

**关键**：A 与 B 不是"两种 OCR"，而是同一 OCR 结果的两种下游用途。B 的实现前提仍是 A——先把每个文件的字段可靠抽出来（见附件 `OCR_fields_CRA_414`），才能既反显、又喂规则。

### OCR 文件字段清单（附件）
`参考资料/OCR_fields_CRA_414 (放款OCR文件字段清单-初稿).xlsx` 是最早与 CRA 团队对齐的底稿：Table of Contents 列出放款阶段 45 类候选 OCR 文件（身份类、HP Agreement 类、HP Form & Other Funding 类、车辆类），每类一个 sheet 定义抽取字段。按业务场景标注了新车/二手/复新/FBR/FBT/进口等适用性，可作为"每个文件抽哪些字段、用于哪类校验"的字段基线。

## 4. 放款案件比例图 —— 需向客户索取的前置数据清单

目标：做一张类似手绘第二图的**放款案件分布/漏斗图**，最终回答"总放款量里有多大比例可以走 STP 自动放款"。

由于 STP 资格是多个条件的**「与」关系**（同时满足才合格），仅有各维度的单独占比无法直接推出 STP 比例，需要客户按下面两部分提供。

### 4.1 基数（100% 基准）
- [ ] 统计口径与周期：如"月均放款件数""近 12 个月放款件数/金额"
- [ ] 放款总件数（件）
- [ ] 放款总金额（RM）

### 4.2 各业务维度的单项占比（每项占总量的 %）
> 对应第二图里的 担保/企/FBR/二手/人工核 等分块

| # | 维度 | 需要的拆分占比 | 对应 STP 条件 |
|---|------|---------------|--------------|
| 1 | 主体类型 | 个人 % / 非个人(企业) % | 条件 1 |
| 2 | 车辆类型 | 新车 % / 二手 % / 复新(Recond) % | 条件 2 |
| 3 | 融资模式 | 正常 % / FBR % / FBT % | 条件 5 |
| 4 | 担保 | 有担保人 % / 无担保 % | 影响复杂度 |
| 5 | 清偿 | 有 payoff % / 无 payoff % | 条件 4 |
| 6 | 定存质押 | 有 FD pledge % / 无 % | 条件 6 |
| 7 | 车商类型 | Panel % / Non-panel %；其中 Floor stock 车商 % | 条件 7 |
| 8 | 受益人 | 单一受益人且与 dealer 系统一致 % / 其他 % | 条件 3 |
| 9 | 签约方式 | E-Acceptance % / Manual(人工核) % | 影响文书处理 |
| 10 | 批复时效 | 放款时批复在 90 天内 % / 超期 % | 2.2 时效闸 |

### 4.3 关键：STP「干净案件」联合占比（最重要，单项占比替代不了）
- [ ] **同时满足全部 7 条硬性资格的案件占总量的 %**（客户现有经验估计即可）
      —— 即"个人 + 新车 + 单一一致受益人 + 无 payoff + 非 FBT + 无 FD 质押 + 非 floor stock 车商 + 批复未超期"的合计比例
- [ ] 若无法直接给联合占比，请提供**主要"不合格原因"的构成**（例：不合格案件中，二手车占 X%、有担保占 Y%、企业占 Z%…），用于漏斗逐层扣减估算

### 4.4 （可选，做 OCR 侧分布图时补充）
- [ ] 每类放款文件的平均出现张数 / 案件覆盖率
- [ ] 各文件当前的 OCR 可识别率 / 需人工校准比例
