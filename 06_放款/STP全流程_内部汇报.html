01

为什么做 STP 放款

STP 定义：Sales 将放款申请提交给 CRA 后，直至完成放款（funding），全程无需 CRA 人工经手执行动作。

V1

释放 CRA 人力

干净案件的录入、核对、执行由系统完成，CRA 聚焦复杂与例外案件。

V2

缩短放款时效

合格案件免排队等待人工维护与授权，提交后自动完成打款与文书。

V3

风控一致性

校验规则系统化统一执行，不依赖个人经验；全程留痕（Defect Code、STP 标识、System teller ID），可审计可统计。

02

核心模型：一条主干，末端分流

所有放款案件走同一条主干；STP 是主干末端的自动化增强，不是另一条独立流程。

关键口径：OCR 只承担「字段填入 / 反显」，不替代复核；复核对所有案件始终存在（人工，或由专家规则系统化执行）。STP 自动化的是放款执行动作（建户 / 打款 / 文书 / 邮件），不是复核本身。

03

STP 直通条件（9 条 + 时效闸 + 双开关）

直通只面向「简单、干净、无风险裁量」的案件。9 条须同时满足，任一不满足即落人工。口径说明：在 FRS 原 7 条基础上，经业务确认新增 E-Acceptance 与 Panel Dealer 两条，进一步收紧直通范围。

01

个人 Individual

公司 / 合伙涉及决议、授权签字人、多担保人、多语言文书，判断复杂。

02

新车 New car

二手 / 复新需验 VOC、payoff、车检、AP 进口证等额外材料。

03

E-Acceptance 电子签约新增

签约数据与协议日期系统内生成、文书系统直出，无需依赖纸质合同提取与人工核对。

04

Panel Dealer 名单内车商新增

名单内车商资质已核、首付款流程标准，无需 Non-Panel 场景的额外凭证核验。

05

唯一受益人且与 Dealer 系统一致

「钱打给谁」无歧义，资金流向已由系统交叉确认。

06

无清偿 No payoff

不涉及替客户结清旧贷、协调旧贷款行、暂记账户处理。

07

非 FBT

车未过户先放款属额外风险敞口，需人工核车商额度与担保。

08

无定存质押 No FD pledge

无需人工核 FD 金额 / 质押期限 / LOSO 与批复一致性。

09

非 Floor Stock 车商

批发融资车商属高风险类别，需额外核整体敞口。

＋ 时效硬闸：90 天三层级校验

  1. 当前日期 ≤ 首次批复日 + 90 天 → 放行；否则查下一层
  2. （FBR/FBT）车辆注册日缺失 → 拦；注册日 ≤ 首批日 + 90 天 → 放行；否则查下一层
  3. LOU 展期日缺失 → 拦；当前日期 ≤ LOU 展期日 + 90 天 → 放行；否则拦
STP_SWITCH

全局总开关，默认 OFF。管理层的「一键刹车」——ON 时合格案子走自动放款，OFF 时即使合格也降级回 CRA Authorizer 人工。运营级风控抓手。

Full Maintenance Indicator

Yes：放款→文书→邮件一次到底；No：只做到放款，转 Post Maintenance 队列人工补做后续文书 / 账务。

04

全流程与角色

四个角色、八个流程段。STP 场景下，系统即第四个作业者（独立 System teller ID 留痕）。

Sales 销售

收齐材料上传、E-Hakmilik 抵押登记、查 FIS / Dealer 资格、提交放款申请。

CRA Checker / Maintenance

OCR 结果确认、放款信息维护、缺陷处理、规则未过案件人工核对。

CRA Authorizer

放款授权；限额＝批准额+费用+税；与最近 checker 不同人（双人原则）。

System / AIOCR + 专家规则

分类、提取、交叉验证、规则自动校验、（STP）自动放款。

  1. Sales 提交段
    E-Hakmilik 登记 → FIS 查询 → Dealer 资格 → 上传 → 提交（触发 Host Acceptance：CIF / 额度 / 抵押创建）
  2. 系统预处理
    文件分类 → 完整性校验 → OCR 提取 → 交叉验证
  3. 预分流
    交叉验证通过且自动路由 ON → 专家规则；否则 → CRA 人工队列
  4. 专家规则校验
    14 类规则；通过 → STP 决策；失败 → 人工队列 + 自动登记缺陷
  5. 人工维护 / 授权
    （非 STP 或开关 OFF）Checker 维护 → Authorizer 授权
  6. 放款执行（两路共用）
    Host Maintenance → 建户 → 打款 → 文书生成 → 邮件；接口超时进 Error Queue
  7. 收尾
    Full Maintenance 一次做完；否则 → Post Maintenance 补做
  8. 放款后
    LHDN 电子印花税、RBS / eTracker 状态回传、对账 / 绩效报表
05

AIOCR：定位、需求与功能

OCR 是 STP 的地基——先把字段可靠抽出来，反显才有内容、规则才有输入、直通才有前提。

5.1定位与两层用途

全案件通用A · 反显填入（提效）

字段自动回填放款维护页，CRA 由「手工敲」变「目视核对 + 确认」；三色状态监控进度。人始终在环。

STP 候选B · 支撑规则自动校验（免检铺路）

交叉验证通过后喂给专家规则全量自动核对；全过则复核环节由规则系统化执行，案件具备直通前提。

5.3功能：四个动作 + 交付逻辑
  1. 自动分类
    上传无需预选类型，自动识别文书类别（含一个 PDF 多份文书拆分）。
  2. 字段提取
    按各文书字段清单提取结构化数据，产出置信度。
  3. 文件规则核验（OCR 工作台）
    完整性、跨文件一致性、日期/金额/固定值等确定性校验；低置信推人工目视校准。
  4. 结果交付（CDM）
    结构化数据写入 CDM，CRA 端直接拉取，由放款团队决定界面填充方式。

双阶段校验：两个阶段、两个工作台、各管一层规则；提交后前端加载动效，结果返回主页反显供二次确认。

5.4职责边界四原则
P1

数据来源定「是否 OCR」

已有 / 系统文书 → 复用；外部新增文书 → OCR 提取。

P2

可确定性定「是否自动」

能写成公式且有对照物 → 引擎自动跑；需人眼判断 → 留工作台。

P3

置信度定「分流」

高置信 + 规则全过 → 自动确认；低置信 / 失败 / 孤立字段 → 推工作台。

P4

最终裁量权归 CRA

OCR / 规则只出结果与建议；Confirm / Override / 放行始终在人。

06

上下游交互

↑ 上游（输入）
  • 签约模块：Acceptance 完成是前提；签约文书归档为 OCR 比对基准（Version 1）
  • 审批链路：首次批复日（90 天基准）、CED 批准额度
  • CILT：V1 vs V2 差异熔断切变更流程，审计字段强制 Reason Code
↔ 本阶段横向
  • FIS / JPJ：抵押登记与车辆注册状态
  • Dealer 管理：Panel / FBR/FBT 资格、Floor Stock 指标
  • HOST 核心：建户、打款；超时重试 + Error Queue
  • AIOCR 引擎：分类 / 提取 / 交叉验证
↓ 下游（产出）
  • 文书与邮件：合并 PDF（专属 PIN 加密）、多语言模板
  • LHDN：电子印花税批量 XML
  • RBS / eTracker：放款状态回传，客户侧可查
  • 报表 / EDW：对账、绩效、STP Indicator 过滤
