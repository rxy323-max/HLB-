文件中心与 OCR

A.2 – A.11 · 六处

冲突 01

非 OCR 文件的定义，与它后续的全部处理动作互斥

待决策高
A.2非 OCR 文件「从此入口上传的文件仅做保存，不进行分类、提取和校验」
A.5「属于非 OCR 范围的单文件上传，则直接手动标记具体分类」
A.7.1 / A.11Manual Check Results 下的文件「同样配置有专家规则」，由人工逐条核验
影响按 A.2 的字面读，Manual Check Results 这个页面不该存在——里面的文件既被分了类，也被校了规则。开发若以 A.2 为准，会把非 OCR 文件做成纯附件，整条人工核验链路落空。
建议A.2 改为「不经过大模型自动分类与提取；分类由人工标记，规则由人工核验」。这是措辞问题不是逻辑问题，但它是全文第一个定义，误导成本最高。
冲突 02

Others 文件被一条规则送进 Manual Check，又被另一条挡在门外

待决策高
A.5「所有标记为 Others 的文件，在提交后统一并入 Manual Check 页面进行规则校验」
A.11「不在专家规则清单范围内的文件不在本页面展示，仅保留在 File List 中」
影响Others 按定义就是系统归不了类的文件，通常没有映射的专家规则。A.5 把它们全部送进 Manual Check，A.11 又把没有规则的挡回去——同一批文件，两条规则给出相反的去向。
建议拆成两种子情形写清楚：已被人工标记为具体类型的（有规则 → 进 Manual Check）；提交时仍是 Others 的（无规则 → 只留 File List）。后者还需要补一条提交前提示，否则这些文件会静默地不被任何人核。
冲突 03

系统文书归 Case 级，但角色化的入口里没有它的位置

原型已定案中
A.3.1上传入口按角色区分：主借人、担保人、卖家——没有 Case 级入口
A.4系统文书「归属于 Case 级别，不并入其他角色入口」
影响A.4 要求 Case 级文书独立存在，A.3.1 的入口清单里却没有承载它的地方。HP Agreement 已签署、Application Form、Biometric Result 这类系统归档文书因此无处可去。
现状已按你的指示去掉抽屉里的 Case 入口。这些文件保留 Case 归属、在 All Files 下可见、Subject 列直接标注为 Case——既不进抽屉，也没被折进任何角色，算是同时满足了两条。
待确认如果这个形态可以，A.4 需要补一句「Case 级文书不设独立入口，在全部文件下按 Case 标识展示」。如果要严格按 A.4 做，则需要恢复一个只读的 Case 分组。
冲突 04

担保人被删除后，遗留文件显示在哪个入口没有定义

待决策中
A.3.3「若担保人被删除，文件中心中该担保人对应的文件不会被自动覆盖或删除，须由人工主动删除」
A.4全部文件入口「按角色分别展示」——而这个角色此刻已经不存在了
影响文档保证了文件不丢，却没说它们此后挂在哪。若实现时按现存担保人渲染入口，这批文件会从界面上消失但仍在库里——比直接删掉更糟。
建议补一句归属规则。原型目前保留一个置灰的Guarantor 2 · removed from application入口，这是我补的、文档里没有，请确认是否采纳。
冲突 05

全量重跑规则时，人工的豁免与合格标记保不保留

待决策高
A.7任意文件变化即对全 Case 重跑全部规则；「只保留最新一次的校验结果，不保留历史快照」
A.9.2Justification（豁免）与标记合格，是 CRA 对校验结果的手动覆盖
A.15案件打回后，Sales 同样有权改写 CRA 已标记的规则结果
影响三条放在一起，全文没有任何一句说明重跑之后人工的豁免与合格标记是保留还是清空。这直接决定返工量：若清空，CRA 每替换一份文件就要把几十条已处置的规则重做一遍；若保留，又要回答「文件都换了，旧豁免还算数吗」。
建议明确二选一，我的倾向是：人工处置意见按规则 ID 保留，仅当该规则关联的文件被替换时才失效。这样既不丢工作量，也不会让豁免盖在一份已经换掉的文件上。无论选哪种，都必须写进 A.7。
冲突 06

混合上传与逐份上传的两种预览形态，缺少判定依据

原型已定案中
A.11「①混合上传平铺展示全部文件与规则；②逐份上传则一份文件对应一个查看窗口」
A.3.2混合主文件「后续分类环节再将其拆分为 OCR 文件与非 OCR 文件分别处理」
影响拆分之后，系统凭什么还知道这批文件原本是一次混合上传？文档没有说这个标记要持久化。没有它，A.11 的两种形态无从选择——这也是原型此前两种模式看起来一模一样的根因。
现状已去掉预览页的模式切换开关，改为文件自带上传形态标记（上传时写入）：列表里点开混合上传的文件，一个窗口平铺全部；点开逐份上传的文件，只显示它自己。左侧规则集始终是该 Case 的全量，不随预览变化。
建议A.3.2 补一句：拆分时在子文件上保留原始上传批次标识，供 A.11 判定展示形态。

CRA 工作台

A.8 – A.14 · 六处

冲突 07

刷新规则到底碰不碰 Defect：同一节里三句话互相打架

原型已定案高
A.10.2 ①「摘要区域的『刷新』按钮不会覆盖此记录，需单独更新」
A.10.2 ②「每次点击『刷新规则』按钮时，系统会先清空 Defect List 中上一次所有『创建来源 = System』的记录」
A.10.2 ③「三者完全解耦，避免出现『用户已针对存量 Defect 做了部分处理，却被整体刷新覆盖』的联动异常」
影响同一节里的三句话：第一句说刷新不动 Defect，第二句说刷新先清空一批 Defect，第三句给出的理由恰恰是在描述第二句会造成的后果。中间那句就是它自己结尾要避免的那种联动。
现状按你 8/28 的指示实现为刷新完全不碰 Defect，来源清空由人工逐条处理。原型的刷新只更新规则结论，Defect List 一条不动。
建议删掉 A.10.2 的「刷新联动规则（最终方案）」整段，保留前段与结尾。这是纯回写，不需要再讨论。
冲突 08

Sync from OCR 的同步范围写了必要文件清单，但没有对应设计

待决策中
A.10.4「反显填入的字段范围包括：必要文件清单的勾选等」
B.5Next 按钮「仅当 Case 下所有必填内容均已完成时才激活」——必要文件清单是其中一项
影响这是缺口不是矛盾：原型的同步弹框目前只覆盖 Data Maintenance 的字段，没有同步 File Check List 的勾选。而这份清单正是 Next 能否点亮的条件之一，不同步就得手工逐项勾——A.10.4 写它是有道理的。
建议确认是否要做。要做的话，同步弹框需要多一个 File Check List 分组，并说明 OCR 侧凭什么判定某份必要文件「已具备」——是按文件类型存在，还是按该类型下所有规则通过。这两种口径结果不同。
冲突 09

提交前校验按「来源」比对，会对人工登记的 Defect 误报

原型已定案高
A.10.5比对「未通过规则数量」与 Defect List 中「创建来源 = System 的记录数量」
A.12规则与 Defect 之间存在唯一映射（规则 ID → Defect Code / Category），这才是判断有没有登记的依据
影响若 CRA 对某条未通过规则手动建了 Defect（来源 = User），按 A.10.5 的口径它不计入，系统仍会提示「有未登记的规则」。人越认真处理，误报越多。
现状原型按 A.12 的映射实现：统计的是「没有任何关联 Defect 的未通过规则数」，与创建来源无关。单条创建和一键创建也共用这个映射去重，不会重复建。
建议A.10.5 的比对口径改写为按映射判断。「创建来源」字段仍然保留——它对刷新逻辑和审计有用，只是不该拿来做这个校验。
冲突 10

三层判断里的「文件判断」层，全文没有第二处定义

待决策中
A.8三层判断表的中间层：「文件判断 / Defect 登记 / 已确认 · 需更换」
A.9.2把「现场直接更换文件」写成规则处置的一种手段，而不是文件的一种状态
影响「已确认 / 需更换」这个状态，全文再没有第二处提到：谁设置、存在哪、在哪个界面看得到，都没有写。开发要么凭空造一套文件状态机，要么直接忽略这一层——两种都不好。
建议二选一。要么给文件加一个真实状态并定义界面；要么把这一层从表里去掉——按现在的写法，它只是「Defect 登记」的另一种说法，三层其实是两层。我倾向后者，因为规则层已经承载了处置，文件层再来一遍会造成两处记录不一致。
冲突 11

「固定处理时序」与工作台的刷新、同步按钮自相排斥

待决策低
A.10「CRA 处理文件中心存在固定的处理时序要求：须先进入文件中心…再返回工作台处理后续信息」
A.10.3 / A.10.4工作台提供「从 OCR 刷新规则结果」与「Sync from OCR」两个按钮
影响如果时序真的固定，工作台就不需要刷新和同步——数据进来时已经是最新的。既然给了这两个按钮，说明来回切换是常态。「固定的时序要求」这个措辞可能被实现成强制拦截（未进文件中心就禁用工作台），那就把常态操作堵死了。
建议改为「推荐顺序」，并明确不做强制校验。
冲突 12

Defect Team 在未分配案件上能不能操作 Defect List

待决策低
A.13Inquiry 模式（案件尚未分配处理人）下，「Defect List 及新版摘要区域均不可操作」
A.14Defect Team 的核心工作「聚焦于 Defect List」——复核整改并标记 Verified
影响文档没说 Defect Team 接手一个退回件算不算「已分配处理人」。若不算，A.13 会把 A.14 描述的核心工作直接锁死。
建议A.13 补一句：Defect Team 认领后案件视为已分配，Defect List 对其可操作，其余区域维持只读。

STP 判断

B.2 – B.5 与规则附录 · 四处

冲突 13

STP 资格既说可以提前判断并提示，又说只在提交时判断

原型已定案中
B.3 ①「因此系统可提前判断案件是否满足资格，并在页面上进行相应提示」
B.3 ③「当前设计为：仅当 CRA 审核完所有内容并点击提交时，系统才判断该案件是走 STP…」
影响两句都留在文档里，开发会同时做一个常驻的 STP 资格提示条和一个提交时判断。两者一旦不一致（提示说合格、提交后路由给 Authorizer），信任度立刻崩掉。
现状原型只做提交时判断，页面上没有任何常驻的 STP 资格提示，符合第三句。
建议删掉首句的「并在页面上进行相应提示」。前半句（当前逻辑固定、理论上可提前算）作为背景保留没问题，但不能读成一个界面要求。
冲突 14

「必填内容」一词在 B.2 与 B.5 指代不同，导致一条死分支

待决策中
B.5Next 按钮「仅当 Case 下所有必填内容（数据维护、放款信息维护等）均已完成时才激活可点击」
B.2STP 决策模块中判断「必要文件与信息是否已获取？未获取则路由至 CRA Authorization」
影响如果两处说的是同一个集合，那么按钮置灰已经保证了它成立，B.2 这条分支永远走不到——是死支。如果不是同一个集合（很可能不是：B.5 说的是维护字段，B.2 说的是文件），那文档从未说明二者的差别，实现时极易做成同一个检查，于是缺文件的案件会被直接放行到 STP。
建议把两个集合分别命名、分别列举。这条看起来是流程图的小瑕疵，实际暴露的是「必填内容」这个词在全文指代不清——它同时被用来指字段、文件和规则结论。
冲突 15

STP 条件说是 9 条，实际 10 条，且全文没有清单

待决策低
B.3 ①「当前 STP 资格判断为固定判断逻辑，共由 9 个确定条件构成」
B.3 末「除上述 9 个条件外，若案件审核时长超过 90 天，同样无法触发 STP 流程」
影响实际是 10 个判断。更要紧的是：这 9 条在全文任何地方都没有列出来。STP 是这次改造的核心产出，它的准入条件却只有一个数字。
建议补一张编号清单，把 10 个条件逐条写明（含 90 天时限），并标注每条的取数来源。没有这张表，STP 判断无法测试，也无法向业务确认。
冲突 16

A.12 要求的映射列，在已签署的规则附录里还不存在

待决策高
A.12「CDM 侧需在现有的专家规则清单中新增一列，记录对应的『OCR 规则 ID』」，并说明该映射「是『创建 Defect』功能的基础」
规则附录signoff version 的现有列：Mandatory Document / business rule checking / Rule Engine Type / Value to Verify / Base Value / DEFECT_ID / DEFECT_CODE / DEFECT_CATEGORY / DEFECT_TYPE —— 没有 OCR 规则 ID，也没有 Severity
影响这不是设计矛盾，是排期前置项：映射列不补齐，单条创建和一键创建 Defect 都做不出来，A.10.5 的提交前校验也没有比对依据。附录已经签署，补列需要走变更。
建议尽早启动附录变更，补两列：OCR_RULE_ID 与 SEVERITY。Severity 虽然 v2 正文没提，但没有它就无法区分「必须拦截」和「提示即可」的规则——目前原型里所有未通过规则一视同仁，这多半不是业务想要的。

建议的处理顺序

先回写、不需要讨论的 5 条：07（刷新不碰 Defect）、09（按映射比对）、13（只在提交时判断 STP）、03（Case 级归属）、06（上传形态标记）。这几条你已经拍过板，原型也照做了，文档跟上即可。

需要你决策、且会影响开发量的 4 条：05（重跑保不保留人工意见）最重要，直接决定 CRA 的返工量；02（Others 去向）和 01（非 OCR 定义）建议一起改，它们是同一处措辞引起的；16（附录补列）是排期前置，越早启动越好。

其余 7 条是措辞与边界补充，可以合并到下一版文档一次性处理，不阻塞当前开发。
