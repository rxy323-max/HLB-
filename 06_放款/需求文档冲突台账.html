「原型已跟着改」是我按 FSD 直接调整过的，两个原型都已更新并测过。「悬而未决」包含 FSD 自己标注 To Be Confirmed 的项，以及从 v2 一路带到 FSD 仍然没有写清的项。

一、FSD 推翻了 v2

这四条不是措辞差异，是规则方向相反。按 v2 实现的部分需要回头改。原型已按 FSD 调整。

反转 R1

删除担保人时，他的文件是留着还是一起删

原型已改高
v2 · A.3.3
担保人被删除，文件中心中该担保人对应的文件不会被自动覆盖或删除，须由人工主动删除
FSD · 2.7.3
系统提示 Sales：该担保人名下所有文件将一并自动移出在用清单，转入 Deleted Files，删除记录留档
影响v2 要求「孤儿文件」留在原地等人工处理，FSD 要求系统自动清理。两者对应的界面完全不同：前者需要一个已删担保人的残留入口，后者不需要。
已改原型删掉了那个置灰的「Guarantor 2 · removed from application」入口，改为该担保人的四份文件自动进入 Deleted 列表，删除原因写「Guarantor removed from application」。
反转 R2

已删除的文件能不能恢复

原型已改高
v2 · A.6 / 原型
删除后的文件进入「已删除」列表，保留删除人、时间与原因，随时可恢复
FSD · 2.7.7
已删除文件不可预览，且不可恢复（cannot be restored）
影响删除从可逆操作变成不可逆操作。原型此前的 Restore 按钮按 FSD 是不该存在的。
已改移除 Restore 按钮与恢复逻辑，Deleted 列表的操作列改为「Record only」，删除确认弹框和左栏说明都改成「保留记录，不可恢复」。
反转 R3

系统文书挂在 Case 下，还是挂在角色下

原型已改高
v2 · A.4
系统文书归属于 Case 级别，不并入其他角色入口
FSD · 2.7.5
系统文书归属于对应主体，应包含在主借人 / 担保人 / 卖家的各自入口下，创建人记为 System
影响你上一轮说「抽屉里不该有 Case 入口」是对的，而且 FSD 比这更进一步——不只是没有 Case 入口，系统文书本身就应该归到具体角色下。我之前给它们保留了一个 Case 标签，那是按 v2 A.4 做的，现在是错的。
已改2nd Schedule、HP Agreement 已签署、Application Form 三份系统文书归入主借人，Subject 列显示 Main Applicant，Source 列仍为 System。
反转 R4

案件打回后，Sales 能不能改 CRA 已标记的规则结果

原型符合中
v2 · A.15
Sales 对 CRA 已标记的规则结果同样拥有编辑权限，并非只读；若不认同 CRA 的判断，可自行改回 Justification / 通过
FSD · 2.9
Sales 可访问 File List；对 Cross Validation 与 Manual Check Results 页面不得进行任何操作，因此不能处理或修改 CRA 已标记的规则结果
影响v2 把 Sales 写成规则结果的共同处置人，FSD 把它收回成纯只读。这条同时影响权限矩阵和「打回—整改」的闭环设计：按 FSD，Sales 整改只有两个动作——重传文件、在 Defect List 勾 Rectified。
现状原型放款阶段的 Sales 权限本来就是up:1, cls:0, rule:0，与 FSD 一致，不用改。但申请阶段的 Sales 仍是可处置的——那部分不在这份 FSD 范围内，需要确认是否同步收紧。

二、FSD 内部矛盾

同一份文档里前后打架，或表述会被实现成相反的东西。

冲突 C1

提交按钮到底卡不卡：3.10.8 说卡，3.11.2 说不卡

待决策高
3.10.8CRA 提交放款信息时须通过 a–e 五项勾稽校验，「The submit button is only enabled if all validation passes」
3.11.2「Clicking Next shall not be hard-blocked solely because unresolved Defects or unconfirmed rule items still exist」
影响这是同一个页面右下角的同一个提交动作。两条可以调和——3.11.2 说的是「不因未处理的规则和缺陷而卡」，3.10.8 说的是数据勾稽——但文档没有一处说明这是两类不同的门。开发很可能二选一实现：要么把勾稽也放行，要么把规则也拦住。
建议把 Next 的启用条件写成一句话：CRA Completed 已勾选，且 3.10.8 的 a–e 勾稽全部通过；未处理的规则与未登记的缺陷只提示、不拦截。
现状原型目前只做了 CRA Completed 这道门。3.10.8 的 a–e 勾稽需要 Approved Loan Amount、Handling Fee、GST、IBG / Transfer / Suspense / Advise 等字段，超出当前原型的数据模型，没有实现。要不要补，看你。
冲突 C2

必要文件清单有三个口径，FSD 自己承认它们对不齐

待决策高
2.7.4系统里有三套与必要文件相关的清单口径：Sales 实际上传的文件、按 Document Type 触发的校验规则、CRA 的 Mandatory File Checklist——「these scopes are not fully aligned」
3.9.2头部摘要须展示「the number of mandatory files required for the Case and the number of files already uploaded」——但没说取哪个口径
影响头部摘要的「必要文件数 / 已上传数」这个分母到底是谁，直接决定 CRA 看到的完成度是否可信。三个口径给出三个不同的分母。FSD 自己也说「Ideally, scope (a) and scope (c) should be aligned」——但没有说这次改不改。
建议明确摘要以 CRA Mandatory File Checklist（scope c）为准，并把参数表 18.20 定为唯一来源。若本期不做对齐，至少要在摘要上标注口径，否则数字会被当成事实。
冲突 C3

误删担保人的后果是不可逆的，但提示里没写

待决策中
2.7.3删除担保人时，「the system shall prompt Sales that all files associated with the guarantor will also be automatically deleted」
2.7.7已删除文件「cannot be previewed; and cannot be restored」
影响两条单独看都成立，合起来是：Sales 误删一个担保人，那批文件永久回不来，只能让客户重新提供。2.7.3 只说要「提示」，没说这个提示必须讲明不可逆。
建议提示文案写明后果与数量，例如「将同时删除该担保人名下 4 份文件，删除后无法恢复，需重新上传」。这是一句文案，但少了它就是一个数据丢失事故。
冲突 C4

STP 条件清单在三处给出三个口径，且明说不封闭

待决策中
4.1.1列出 a–h 共 8 条业务场景限制（h 为 90 天三级判断）
4.1.2决策表列出 4 步：①场景适合 ②必要文件与信息齐备 ③未解决 Defect 为 0 ④STP 开关 ON
3.11.3STP 资格「shall include, but is not limited to」开关已开 + 未解决 Defect 为 0
影响4.1.1 的 8 条是「场景限制」，4.1.2 的 ②③④ 是另外三道门，两者不是同一层。而 not limited to 意味着清单不封闭——测试无从写起，业务也无法确认。v2 当时说 9 条，和这两处都对不上。
建议出一张封闭的编号表，把「场景限制」和「放行门」分成两组列全，去掉 not limited to。这是 STP 最核心的规则，目前没有一处能当依据。
冲突 C5

STP 资格既说可以提前判断并在页面提示，又说只在 Next 时判断

原型已定案中
4.1.2 ①「the system may perform a preliminary assessment in advance and provide the corresponding indication on the page」
4.1.2 ③「for system extensibility, the current design is that the final STP routing decision shall only be made after CRA... clicks Next」
影响v2 里就有这个矛盾，FSD 原样保留了。两句都在，开发会同时做一个常驻的 STP 资格提示条和一个提交时判断；两者一旦不一致，提示就成了噪音。
建议删掉「and provide the corresponding indication on the page」。原型只做提交时判断，页面上没有任何常驻 STP 提示。
冲突 C6

Defect 解耦的通则，与它自己的方法 ③ 表面冲突

原型已实现中
3.9.7 通则「Neither function shall automatically create, overwrite, or delete any records in the Defect List」
3.9.7 ③Synchronize System Defects 会为失败规则创建 Defect，并删除那些对应规则已转为 Passed 的 System 来源记录
影响实质上不矛盾——通则约束的是 Refresh 与 Sync from OCR 两个功能的副作用，③ 是用户主动点的独立按钮。但通则的措辞太绝对，容易被读成「任何情况下都不删」，从而把 ③ 实现成只增不删。
建议通则补一句「③ 除外，且仅在用户主动触发时生效」。
顺带一提：v2 的 A.10.2 在这里是真矛盾（刷新会清空 System 记录），FSD 已经修好了——现在刷新完全不碰 Defect，删除只发生在方法 ③。
现状原型已按 ③ 实现：Defect List 区域新增「Sync System Defects」按钮，补建缺失的、清掉规则已通过的 System 记录，User 来源一条不动。
冲突 C7

「强制处理时序」与刷新机制互相排斥

待决策低
3.9.1CRA「shall follow the required processing sequence」：先进文件中心复核，再回工作台
3.9.2同一经手人未发生流转时不自动刷新，用户可手动点击「Refresh Rule Results」取最新结果
影响既然设计了手动刷新，说明来回切换是常态。把 required sequence 实现成强制拦截（没进过文件中心就禁用工作台）会堵死常态操作。
建议改为「推荐顺序」，并写明不做强制校验。
冲突 C8

交叉引用指向一个不存在的章节

待决策低
4.1.2「Refer to Section 3.9.9 for details」
目录3.9 下只到 3.9.8；Next 按钮与提交时序在 3.11
影响小问题，但 STP 的时序说明正是靠这条引用串起来的，读者会在 3.9 里翻不到。
建议改为 3.11。

三、悬而未决

FSD 自己标注为待确认的，以及从 v2 一路带过来仍然没有写清的。

未决 O1

全量重跑规则时，人工的豁免与合格标记保不保留

待决策高
2.8.3任一文件变化即对全 Case 重跑全部规则；「the system shall retain only the latest validation result. Historical validation snapshots will not be retained」
3.9.5Justification 与手工标记 Passed，是 CRA 对校验结果的人工覆盖，处理后计入 Passed
影响这条从 v2 带到 FSD，仍然没有任何一句说明重跑之后人工的豁免与合格标记是保留还是清空。它直接决定 CRA 的返工量：若清空，每替换一份文件就要把几十条已处置的规则重做一遍。这是整份台账里最要紧的一条。
建议明确二选一。我的倾向：人工处置意见按规则 ID 保留，仅当该规则关联的文件被替换时才失效——既不丢工作量，也不会让豁免盖在一份已经换掉的文件上。写进 2.8.3。
未决 O2

未勾 Full Maintenance 的 STP 案件走到哪一步停

FSD 标注 TBC中
4.2「To Be Confirmed：need to confirm whether Cases without the Full Maintenance Indicator selected should stop after the disbursement step and then be routed to Post Maintenance」
影响影响 STP 直通的终点在哪。原型的 STP 完成提示目前只说「触发放款接口」，没有区分这两种落点。
建议确认后我把两种落点做进 Next 的结果提示，让演示时能讲清「直通到底」和「直通到放款后转 Post Maintenance」的差别。
未决 O3

规则附录仍缺 OCR 规则 ID 与 Severity 两列

排期前置中
3.9.7三种创建方式的去重「shall determine whether a rule has already been associated with a Defect record based on the configured Rule-to-Defect Mapping」
规则附录signoff version 现有列中没有 OCR 规则 ID，也没有 Severity
影响映射表是三种 Defect 创建方式和 3.11.2 提交前校验的共同基础。列不补齐，这四个功能都没有依据。附录已签署，补列要走变更。
建议尽早启动变更，补 OCR_RULE_ID 与 SEVERITY。Severity 虽然 FSD 正文没提，但没有它就无法区分「必须拦截」和「提示即可」的规则——目前原型对所有失败规则一视同仁。
未决 O4

30 天 instinct 的触发细节还没给

等 Risk team低
2.3「Waiting for Risk team to provide details on the 30-day instinct」
影响不影响文件中心与工作台两个原型，但会影响 lodgment 触发的时机判断。
建议跟进 Risk team，明确它与 4.1.1(h) 那套 90 天三级判断是否有交集。
未决 O5

申请阶段的 Sales 规则处置权限是否同步收紧

待决策低
FSD 2.9放款阶段 Sales 对规则页面不得进行任何操作——但这份 FSD 只覆盖 Disbursement
原型申请阶段 Sales 仍是上传 + 确认分类 + 处置规则三项全开
影响申请阶段 Sales 既是提交人又是校验人，这在放款阶段已经被 FSD 明确否掉了。申请阶段是否保留这个设定，需要单独确认——它不在这份 FSD 的范围内。
建议确认申请阶段的定位。若同步收紧，原型的 sales|app 权限要从 rule:1 改为 rule:0。

四、上一版台账里已被 FSD 解决的

这六条不用再讨论，FSD 已经写清楚了。

非 OCR 文件的定义与它后续动作互斥 —— 改写为「默认不经 AI 引擎处理、不做 AI 分类与提取」，不再说「不进行校验」2.7.1 b
Others 文件的去向 —— 无 Document Type 的文件不做规则校验、不进 Manual Check，仅留在 File List 供存储与预览2.7.6 / 2.8.2 / 3.9.4
刷新到底碰不碰 Defect —— 通则明确 Refresh 与 Sync from OCR 都不创建、不覆盖、不删除 Defect3.9.7
提交前校验的比对口径 —— 明确按 Rule-to-Defect Mapping 统计「当前失败且尚未关联任何 Defect」的规则数，与创建来源无关3.11.2
三层判断里悬空的「文件判断」层 —— FSD 没有沿用这张表，问题自然消失—
Defect Team 在未分配案件上的权限 —— 流转清单已明确含 Defect Team 的收发两端3.9.2

建议的处理顺序

先同步给开发的 4 条反转：R1–R4。这些不是待讨论项，是 FSD 已经定稿、但与 v2 相反的规则。若有人还在按 v2 做担保人删除或文件恢复，越早说越好。

需要你决策的 3 条：O1（重跑保不保留人工意见）仍然最重要，从 v2 悬到 FSD 还是没写；C1（提交按钮两道门）会直接改 Next 的实现，我目前只做了 CRA Completed 一道；C2（必要文件三个口径）决定头部摘要那个分母可不可信。

排期前置 1 条：O3 附录补两列，卡着三种 Defect 创建方式和提交前校验。

其余 C3–C8、O2、O4、O5 是文案与边界补充，可以并到下一版一次性处理。
