核心模型

所有放款案件走的是同一条主干；STP 是主干末端的自动化增强，不是另一条独立流程。

关键口径：OCR 只承担「字段填入 / 反显」这一个角色，它不替代复核。复核环节对所有放款案件始终存在。只要过 STP 放款，业务上 OCR 作为填入，仍由 CRA 复核（人工，或由专家规则系统化执行）。STP 自动化的是放款执行动作（建户 / 打款 / 文书 / 邮件），不是复核本身。

01

STP 硬性条件

STP 要免掉人工执行，前提是案子「简单、干净、无风险裁量」。以下 7 条须同时满足，任一不满足即落人工。

01

个人 Individual

公司 / 合伙涉及决议、授权签字人、多担保人、多语言文书，判断复杂，不能免人工。

02

新车 New car

二手 / 复新要验 VOC、payoff、车检、AP 进口证等大量额外材料，变量多。

03

唯一受益人且与 Dealer 系统一致

「钱打给谁」必须无歧义；系统已交叉确认资金流向，无需人工核打款对象。

04

无清偿 No payoff

不涉及替客户结清旧贷，无需算结算金额、协调旧贷款行、处理暂记账户余额。

05

非 FBT

FBT＝车未过户先放款，银行额外风险敞口，需人工核车商额度与担保。

06

无定存质押 No FD pledge

无需人工核 FD 金额 / 质押期限 / LOSO 抵销函与批复的一致性。

07

非 Floor Stock 车商

批发融资车商属高风险类别，放款需额外核车商整体融资敞口。

＋ 时效硬闸：90 天三层级校验

  1. 当前日期 ≤ 首次批复日 + 90 天 → 放行；否则查下一层
  2. （FBR/FBT）车辆注册日缺失 → 拦；注册日 ≤ 首批日 + 90 天 → 放行；否则查下一层
  3. LOU 展期日缺失 → 拦；当前日期 ≤ LOU 展期日 + 90 天 → 放行；否则拦
STP_SWITCH

全局总开关，默认 OFF。管理层的「一键刹车」——ON 时合格案子走自动放款，OFF 时即使合格也降级回 CRA Authorizer 人工。用于上线初期或异常时的运营级风控。

Full Maintenance Indicator

决定放款后收尾是否一次做完。Yes：放款→文书→邮件一次到底；No：只做到放款，状态置 Funded Pending Post Maintenance，转 Post Maintenance 队列由人工补做后续文书 / 账务。

02

放款流程与角色

CRA 放款是所有案件的基础主干，STP 是其上的自动化增强。四个角色、八个主流程段。

Sales 销售

收齐材料上传、触发 E-Hakmilik 抵押登记、查 FIS / Dealer 资格、提交放款申请。

CRA Checker / Maintenance

OCR 结果确认、放款信息维护、缺陷（Defect）处理、规则未过案件的人工核对。

CRA Authorizer 授权人

放款授权把关；限额＝批准额+手续费+GST/SST；不得与最近 checker / 缺陷处理人同人。

System / AIOCR + 专家规则

文件分类、字段提取、交叉验证、规则自动校验、（STP）自动放款。

  1. Sales 提交段
    E-Hakmilik 抵押登记 → FIS 查询（车辆状态 verified/processed）→ Dealer FBR/FBT 资格查询 → 上传文件 → 提交（触发 Host Acceptance：CIF / 额度 / 抵押创建）
  2. 系统预处理
    文件分类 → 完整性校验 → OCR 提取 → 交叉验证
  3. 预分流
    OCR 交叉验证通过且自动路由开关 ON → 专家规则自动校验；否则 → CRA Checker 人工队列
  4. 专家规则校验
    14 类规则；通过 → STP 决策；失败 → 人工队列并自动登记缺陷
  5. 人工维护 / 授权
    （非 STP 或开关 OFF）Checker 维护 → Authorizer 授权
  6. 放款执行（人工与 STP 共用）
    Host Maintenance → Account Creation → Disbursement 打款 → 文书生成（加密 / 非加密 PDF）→ 邮件外发；接口超时进 Error Queue
  7. 收尾
    Full Maintenance 一次做完；非 Full Maintenance → Post Maintenance 补做
  8. 放款后
    LHDN 电子印花税、RBS / eTracker 状态回传、对账 / 绩效报表
03

上下游交互

放款不是孤立环节：上游给输入与比对基准，本阶段横向对接多个系统，下游产出文书、状态与报表。

↑ 上游（输入）
  • 签约模块：Acceptance 完成是前提；E-acceptance 协议日期默认当前工作日；签约文书自动归档，作为 OCR 比对基准（Version 1）
  • 审批链路：首次批复日（90 天校验基准）、CED 批准额度（FD 质押比对基准）
  • CILT：Version 1 vs 发票/VOC 提取 Version 2 比对；差异熔断则切入 CILT 变更；审计字段变更强制 Reason Code
↔ 本阶段横向
  • FIS / JPJ：E-Hakmilik 抵押登记与车辆注册状态；带缓存与总开关；FBR/FBT、IHP 跳过自动查询
  • Dealer 管理：FBR/FBT Undertaking Limit 资格、Floor Stock 指标、Non-panel 提示；Authorizer 登 HOST 查实时额度
  • HOST 核心：Host Acceptance / Maintenance、建户、打款；超时重试 + Error Queue；STP 记 System teller ID
  • AIOCR 引擎：分类 / 提取 / 交叉验证；三色状态监控；人工提前介入记 Manual Process Indicator
↓ 下游（产出）
  • 文书与邮件：Hirer / Guarantor 合并 PDF（专属 PIN 加密）；Infobip / 邮件多语言多版本模板
  • LHDN：电子印花税批量 XML；E-acceptance 嵌 Print Log；担保人文书后缀 _G1/_G2
  • RBS / eTracker：放款状态回查（first release date → IS FUNDED），客户侧显示 Disbursement 状态
  • 报表 / EDW：放款对账（AP_INDICATOR）、HP 绩效、缺陷报表、STP Application Indicator 过滤
04

OCR × CRA 复核工作台（职责边界）

回答两个设计问题：哪些文书进 OCR（按数据来源界定），以及哪些校验放 OCR 引擎、哪些留 CRA 工作台（按可确定性与置信度界定）。

4.1OCR 的两层用途

不是「两种 OCR」，而是同一份 OCR 结果的两种下游用途。B 的前提仍是 A——先把字段可靠抽出来，才能既反显、又喂规则。

全案件通用A · 反显填入（提效）

抽取字段自动回填放款维护页，CRA 由「手工敲」变「目视核对 + 确认」；三色状态监控 OCR 进度。人始终在环里，OCR 是帮手。

STP 候选B · 支撑规则自动校验（免检铺路）

交叉验证通过后，抽取结果喂给专家规则做全量自动核对；全过则该复核环节可由规则替代人工，案子具备走 STP 自动放款的前提。

4.2哪些文书进 OCR —— 按「数据从哪来」界定

放款文书不是都要 OCR。只有外部新增文书才需要 OCR 提取；已在前阶段采集的、或系统自己生成的，直接复用数据。

已有

前阶段（进件/签约）已采集并核验，放款阶段直接复用，不重复 OCR。

NRIC · Passport · Driving License · Seller's IC

系统文书

由系统生成，字段本就结构化在库里，无需 OCR，系统直接提供数据。

HP Agreement & T&C · Application Form · 2nd Schedule · Biometric 结果

需 OCR

放款阶段首次出现的外部文书，须 OCR 抽字段并交叉校验。这就是放款 OCR 的真实范围。

Vehicle Invoice · VOC · Road Tax · Insurance Cover Note · Delivery Order · IBG Letter · FIS/JPJ Result · E-hakmilik · Credit Note(Admin Fee) · Loan Suspense Receipt

4.3校验放哪里 —— OCR 引擎 vs CRA 工作台

OCR 引擎负责「能自动算的」，CRA 工作台负责「要人判断的」。校验规则每条挂一个 Defect Code。

OCR 引擎层 · 自动

高置信提取 + 确定性规则，机器可判定

  • 字段提取：从「需 OCR」文书抽结构化字段
  • 确定性专家规则自动跑：日期比对 / 算术加总 / 固定值(如 Admin fee=RM270) / 金额一致 / 地区匹配 / 表单版本映射
  • 产出：Pass / Fail；失败自动登记对应 Defect Code，二次提交通过后自动置 Rectified

CRA 复核工作台层 · 人工

需人眼判断、无数字对照、或引擎判不了的

  • 结果确认 / 纠错：对每条规则 Confirm / Error / Edit（改 OCR 值 + 填 Reason）
  • 低置信字段：OCR 置信度低于阈值的推人工目视校准
  • 孤立关键字段：无跨文件数字可比对的，须人工目视确认
  • 特殊文书判断：某场景是否缺必备文件、Hard Fail 是否放行等，最终裁量权在 CRA
4.4划分原则（界定边界的四条准则）
P1

数据来源定「是否 OCR」

已有 / 系统文书 → 复用或系统提供，不 OCR；外部新增文书 → OCR 提取。

P2

可确定性定「是否自动」

能写成确定公式、且有数字对照物 → 引擎自动跑；需人眼判断、无对照 → 留 CRA 工作台。

P3

置信度定「分流」

高置信 + 规则全过 → 自动确认（STP 可直通）；低置信 / 规则失败 / 孤立字段 → 推工作台。

P4

最终裁量权归 CRA

OCR / 规则只产出结果与缺陷建议；Confirm / Override / 放行的决定权始终在人。
