Core Model

Every disbursement case runs on the same main pipeline; STP is an automation enhancement at the end of that pipeline, not a separate flow.

Key alignment: OCR plays exactly one role — field population (auto-fill). It does not replace the review step. Review exists for every disbursement case: even on the STP path, OCR only fills in data, and CRA still reviews it (manually, or via systemized expert rules). What STP automates is the disbursement execution actions (account creation / payment / document generation / emailing) — not the review itself.

01

STP Hard Eligibility Rules

STP removes manual execution only for cases that are "simple, clean, and free of risk judgment". All 7 rules below must be met simultaneously; failing any one routes the case to manual handling.

01

Individual

Corporate / partnership cases involve resolutions, authorized signatories, multiple guarantors, and multilingual documents — too much judgment to automate.

02

New car

Used / recond cars require VOC, payoff, inspection, AP import permits and many extra documents — too many variables.

03

Single beneficiary, matching dealer system

"Who receives the money" must be unambiguous; the fund flow is already cross-confirmed by the system, so no manual payee check is needed.

04

No payoff

No settlement of an existing loan — no settlement amount calculation, no coordination with the previous lender, no suspense account handling.

05

Not FBT

FBT = funding before ownership transfer; extra risk exposure for the bank, requiring manual checks on dealer limits and indemnities.

06

No FD pledge

No manual verification of FD amount / pledge tenor / LOSO consistency against the approval.

07

No Floor Stock dealer

Wholesale-financing dealers are a high-risk category; disbursement requires extra checks on the dealer's overall exposure.

＋ Time-validity gate: 90-day three-tier check

  1. Current date ≤ first approval date + 90 days → allow; otherwise check next tier
  2. (FBR/FBT) Vehicle registration date missing → block; registration date ≤ first approval + 90 days → allow; otherwise check next tier
  3. LOU renewal date missing → block; current date ≤ LOU renewal date + 90 days → allow; otherwise block
STP_SWITCH

Global master switch, default OFF. Management's "emergency brake" — when ON, eligible cases go to automated disbursement; when OFF, even eligible cases are downgraded to CRA Authorizer for manual handling. An operational risk control for launch phases and incidents.

Full Maintenance Indicator

Determines whether post-disbursement wrap-up completes in one pass. Yes: disbursement → documents → email, end to end; No: stop after disbursement, set status to Funded Pending Post Maintenance, and hand the case to the Post Maintenance queue for manual follow-up on remaining documents / accounting.

02

Disbursement Process & Roles

CRA disbursement is the base pipeline for all cases; STP is an automation layer on top. Four roles, eight process stages.

Sales

Collect & upload documents, trigger E-Hakmilik lodgement, query FIS / dealer eligibility, submit the disbursement application.

CRA Checker / Maintenance

Confirm OCR results, maintain disbursement data, handle defects, manually verify cases that failed rule validation.

CRA Authorizer

Final authorization; limit = approved amount + fees + GST/SST; must not be the same person as the latest checker / defect handler.

System / AIOCR + Expert Rules

Document classification, field extraction, cross-validation, automated rule checking, (STP) automated disbursement.

  1. Sales submission
    E-Hakmilik lodgement → FIS query (vehicle status verified/processed) → Dealer FBR/FBT eligibility → upload files → submit (triggers Host Acceptance: CIF / facility / collateral creation)
  2. System pre-processing
    Document classification → integrity checks → OCR extraction → cross-validation
  3. Pre-sorting
    OCR cross-check passed and auto-routing switch ON → expert rule validation; otherwise → CRA Checker manual queue
  4. Expert rule validation
    14 rule types; pass → STP decision; fail → manual queue with defects auto-registered
  5. Manual maintenance / authorization
    (Non-STP or switch OFF) Checker maintenance → Authorizer approval
  6. Disbursement execution (shared by manual & STP)
    Host Maintenance → Account Creation → Disbursement payment → document generation (encrypted / unencrypted PDF) → emailing; interface timeouts go to the Error Queue
  7. Wrap-up
    Full Maintenance completes in one pass; otherwise → Post Maintenance follow-up
  8. Post-disbursement
    LHDN e-stamping, RBS / eTracker status sync, reconciliation / performance reports

Upstream / Downstream Interactions

Disbursement is not isolated: upstream provides inputs and comparison baselines, this stage integrates with multiple systems, and downstream produces documents, statuses and reports.

↑ Upstream (inputs)
  • Acceptance module: completed acceptance is the prerequisite; e-acceptance agreement date defaults to the current work date; signed documents are auto-archived as the OCR comparison baseline (Version 1)
  • Approval chain: first approval date (basis for the 90-day check), CED approved amount (basis for FD pledge comparison)
  • CILT: Version 1 vs Version 2 (extracted from invoice/VOC) comparison; discrepancies trigger the CILT amendment flow; audited field changes require a Reason Code
↔ This stage (integrations)
  • FIS / JPJ: E-Hakmilik lodgement and vehicle registration status; cached queries with a master switch; FBR/FBT and IHP skip the automatic query
  • Dealer management: FBR/FBT Undertaking Limit eligibility, Floor Stock indicator, non-panel prompts; Authorizer checks real-time limits in HOST
  • HOST core: Host Acceptance / Maintenance, account creation, payment; timeout retries + Error Queue; STP records a System teller ID
  • AIOCR engine: classification / extraction / cross-validation; three-color status monitoring; early manual intervention sets the Manual Process Indicator
↓ Downstream (outputs)
  • Documents & email: merged Hirer / Guarantor PDF (personal-PIN encrypted); Infobip / email templates, multilingual and multi-version
  • LHDN: e-stamping batch XML; e-acceptance embeds the Print Log; guarantor documents suffixed _G1/_G2
  • RBS / eTracker: disbursement status lookup (first release date → IS FUNDED); customer-facing Disbursement status
  • Reports / EDW: reconciliation (AP_INDICATOR), HP performance, defect reports, STP Application Indicator filtering

OCR × CRA Review Workbench (Responsibility Boundary)

Two design questions answered here: which documents go through OCR (defined by data source), and which checks run in the OCR engine vs. the CRA workbench (defined by determinism and confidence).

4.1Two uses of OCR

Not "two kinds of OCR" — two downstream uses of the same OCR output. B depends on A: fields must be reliably extracted before they can be auto-filled or fed to rules.

All casesA · Auto-fill (efficiency)

Extracted fields auto-populate the disbursement maintenance pages; CRA shifts from "manual typing" to "visual check + confirm"; three-color status tracks OCR progress. A human stays in the loop — OCR is the assistant.

STP candidatesB · Feeding automated rule validation (paving the way for STP)

Once cross-validation passes, extracted results feed the expert rules for a full automated check; if all pass, that review step can be systemized, making the case eligible for STP auto disbursement.

4.2Which documents go through OCR — defined by "where the data comes from"

Not every disbursement document needs OCR. Only newly introduced external documents require OCR extraction; data captured in earlier stages or generated by the system is reused directly.

Already captured

Collected and verified in earlier stages (application / acceptance); reused at disbursement, no repeat OCR.

NRIC · Passport · Driving License · Seller's IC

System-generated

Generated by the system; fields already structured in the database — no OCR needed.

HP Agreement & T&C · Application Form · 2nd Schedule · Biometric result

OCR required

External documents appearing for the first time at disbursement; OCR extracts fields for cross-validation. This is the true scope of disbursement OCR.

Vehicle Invoice · VOC · Road Tax · Insurance Cover Note · Delivery Order · IBG Letter · FIS/JPJ Result · E-hakmilik · Credit Note (Admin Fee) · Loan Suspense Receipt

4.3Where each check runs — OCR engine vs. CRA workbench

The OCR engine handles what can be computed automatically; the CRA workbench handles what requires human judgment. Every validation rule maps to a Defect Code.

OCR Engine layer · Automated

High-confidence extraction + deterministic rules the machine can decide

  • Field extraction: pull structured fields from "OCR required" documents
  • Deterministic expert rules run automatically: date comparison / arithmetic totals / fixed values (e.g. Admin fee = RM270) / amount consistency / region matching / form-version mapping
  • Output: Pass / Fail; failures auto-register the mapped Defect Code, auto-set to Rectified once a resubmission passes

CRA Review Workbench layer · Manual

Needs human judgment, has no numeric counterpart, or the engine cannot decide

  • Result confirmation / correction: Confirm / Error / Edit per rule (correct the OCR value + provide a Reason)
  • Low-confidence fields: OCR results below the confidence threshold go to manual visual calibration
  • Isolated key fields: fields with no cross-document counterpart require visual confirmation
  • Special document judgment: whether a scenario is missing mandatory files, whether a Hard Fail may be released — final discretion rests with CRA
4.4Boundary principles (four criteria)
P1

Data source decides "OCR or not"

Already captured / system-generated → reuse or system-provided, no OCR; new external documents → OCR extraction.

P2

Determinism decides "automated or not"

Expressible as a deterministic formula with a numeric counterpart → engine runs it; requires human judgment or has no counterpart → stays in the CRA workbench.

P3

Confidence decides routing

High confidence + all rules passed → auto-confirmed (STP-eligible); low confidence / failed rules / isolated fields → pushed to the workbench.

P4

Final discretion rests with CRA

OCR / rules only produce results and defect suggestions; the decision to Confirm / Override / release always belongs to a person.
