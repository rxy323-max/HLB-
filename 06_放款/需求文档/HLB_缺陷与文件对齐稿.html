01

现有流程：Batch 2 今天是怎么跑的

这是我们要改的起点，先把它说准，否则很容易改掉一个其实并不存在的问题。

  1. CRA · 工作台 登记 defect

    选 defect category，再选一个 defect type，写 CR remark。 登记时不记录关联哪份文件——现有 defect 结构里没有“关联文件”这个说法。

  2. CRA 退回给 Sales

    案件回到 Sales 手上，Sales 看到的是一条条 defect。

  3. SALES · 从 defect 入口进文件中心 上传新文件

    此刻文件中心是空的：申请阶段、放款阶段已存的文件他一份都看不到。 相当于为这条 defect 单开了一个文件中心，各 defect 之间互相隔离—— 从这个入口传上去的文件，也只在这个入口里能看到。

  4. SALES rectify 这条 defect

    上传和 rectify 是两个独立动作，Sales 要各做一遍。

  5. CRA · defect list verify

    在 defect 列表里直接确认，不需要回文件中心看文件。

生产上的实际做法，比设计更宽松。一份文件常常一次命中多条规则， 但 defect type 现在是单选。CRA 的做法是：选完 category，随便选一个 type， 把其余问题全部写进 CR remark。也就是说——

生产里的一条 defect，事实上已经等于“一份文件的一堆问题”， 而不是“一条规则的一个问题”。我们要做的不是发明新维度，是把这个既成事实变成系统里的显式结构。

口径来源：与张浩确认 defect rules 表（字段定义、defect category number、defect id number 均由 ye 方提供）。 defect type 改多选已定为本方案的做法，表结构支持性仍需 ye 侧确认。

02

核心挑战：七个难点，按“为什么难”排

这七条是三场会反复回到的地方。前四条是结构性的，后三条是它们的衍生。

  • 难点一 · OCR 里其实有两类规则，但只有一类该产生 defect。 一类是 OCR 自己的文件校验规则（为了保证提取准确、供下游反显）， 另一类是配进 OCR 的专家规则。只有后者不过才值得登记缺陷； 前者不过只说明“这份文件读不准”。两类混在同一个告警区里，是 CRA 反复困惑的直接来源。
  • 难点二 · 告警清零与缺陷留存互相冲突。 CDM 的现行逻辑是：所有告警处理完，数据才落库，下游才能反显。 但我们想要的是“创建了 defect，告警仍然保留”——不然缺陷的证据就没了。 这两条规则今天不能同时成立。
  • 难点三 · defect 挂在哪个维度上，一直没定。 挂规则？一份文件命中五条规则就是五条 defect，CRA 要处理五遍，与生产实际相反。 挂 file type？同一 type 下可能有多份文件，第二轮又会新增一份，指代不清。 挂主文件？OCR 会把一个 PDF 拆成多个子文件，主文件层面已经无法区分是哪一部分出的问题。
  • 难点四 · OCR 与非 OCR 的层级根本不对齐。 OCR 有“主文件 → 子文件”两层，非 OCR 只有主文件一层，而专家规则是跟着 file type 跑的。 会上明确说过“非 OCR 你怎么拆——让用户上传时自己拆，对他要求太高了”。 两条路径不在同一维度，任何关联规则都要写两套。
  • 难点五 · 第二轮重传要不要走 OCR，两边都有代价。 走 OCR：能重新提取、能反显、规则能自动重判；代价是必须限死文件类型， 且分类识别可能和目标类型冲突。不走 OCR：文件干净地进 file list， 但 OCR 侧的数字永远不更新，规则只能靠人工断言。
  • 难点六 · 新文件上来之后，旧 defect 和旧文件怎么处置。 旧 defect 删掉，CRA 手写的 remark 就丢了；保留，列表里就会积压已经不成立的条目； 旧文件如果系统自动置为失效，等于一次隐性删除—— “我不知道客户同不同意这么干。”
  • 难点七 · 两边各操作一遍，是最贵的成本。 文件中心处理一遍告警、defect 那边再处理一遍状态，同一件事做两次。
“他既要在这边操作一遍，又要在 OCR 操作一遍，又要在 defect 那边再操作一遍。我觉得是最差的方案。” 张骏 · 09-04 上午场

会上还认真推演过一个更激进的方案：干脆不要 defect，改成一份 log。 结论是不成立——log 只记录“哪一条被替换掉了”， 但“新文件到底有没有解掉 a 规则、谁来判”这个问题它一个字都没回答。 缺陷之所以贵，正是因为它承载了责任人和结论，这部分不能省。

这七条在第 03–08 节逐一被回答；对应的口径结论汇总在第 09 节。

03

方案 · 第一步：把维度定死

这是第三场会最重要的产出，也是后面所有交互的地基。

Anchor

defect 关联的是文件 ID，不是规则，也不是 file type。
一条 defect = 一份文件的一组问题。

file type 决定跑哪些专家规则；专家规则命中在具体的文件 ID 上； defect ID 与 file ID 一一对应。文件 ID 比 file type 承载更多信息， 也能区分同一类型的多个版本——这正是第二轮重传所需要的。

一个主文件里的两个 file type 都有问题，就是两条 defect。 对应地，Sales 退回后要传两次、rectify 两次——这不是设计的粗糙， 而是因为第二轮必须按 file type 锁定重传，两个类型无法合并成一次上传。

“一条 defect 对应一份文件的一组问题”这件事， 落到字段上就是 defect type 多选（口径 6）。 没有多选，这条锚点就只能靠 remark 里的自由文本承载， 场景 c / d 的自动更新也就无处可落。

04

方案 · 第一轮：在文件中心创建，告警不清

缺陷的唯一发源地是文件中心；缺陷的唯一查询地是 CRA 工作台。两者不重叠。

  • 创建入口在文件中心，手动触发。 Cross Validation 详情页与 Manual Check 结果页各提供一个创建按钮， 弹出 defect 弹框，把失败规则的内容快速带入，CRA 确认后落库。
  • 创建后，对应的规则告警保留。 这是本轮设计与现状最大的一处冲突： OCR 需要具备“带告警保存”的能力，否则 CDM 不落库、下游反显拿不到数据。 这是必须提给 OCR 侧的改动。
  • 文件中心不提供查看 defect 的能力。 不建 defect tab、不显示 defect 明细。所有 defect 查询集中在 CRA 工作台， 避免同一份台账出现两个入口、两套数字。
  • Manual Check 结果页提供“一键通过”（全局）， 与文件级别的创建 defect 并列。第一轮的动作是创建。
  • 人工上传第一轮可确定一个或多个 file type。 左侧通栏展示这个 case 涉及的全部专家规则，右侧是不同的文件，CRA 逐条勾选。
05

方案 · 第二轮：锁定文件类型的定向重传

Sales 从 defect 进入文件中心，看到的是一个被收窄过的世界。

Sales 侧 · 从 defect 入口

  • 仅展示关联文件，不是全量文件中心。
  • 可上传新文件，OCR 与非 OCR 两个入口都开放。
  • 文件类型被 defect 锁死，不可选——它就是这条 defect 关联的 file type。
  • 上传成功后新文件生效，defect 一键关联到新文件。
  • 两个 file type 有问题就传两次、rectify 两次。

系统不做的事

  • 不自动删除旧文件，OCR 与 manual 的原文件、子文件全部留在页面上。
  • 不自动把旧文件置为失效——那是一次隐性删除。
  • 客户可以手动删除，结果自负。
  • 传错文件也不做处理，只按原样预览。

OCR 侧的处理口径。第二轮仍走 OCR 的好处是能继续反显； 代价是必须限制文件类型。为此单独设置提示词：只能选目标 file type； 若分类识别与目标文件冲突，OCR 统一输出为 others，不识别、不提取。 传错文件、目标文件缺失，同样输出 others。Sales 通过更换文件自行解决。

Manual Check 侧的展示口径（口径 2 已定）。 左侧只展示这条 defect 所关联 file type 的规则， 屏蔽掉其他已经通过的规则；右侧看新上传文件的原文。 同一次进入若牵涉两条 defect，可以两条一起 rectify。

注意这里和第 06 节的重跑范围并不矛盾： 系统在后台按全案重跑，Sales 在前台只看被收窄的这一段。 Sales 只对自己能动的那份文件负责，全案影响由 CRA 侧承接。

06

方案 · 重跑范围、CRA 复核与四种结果

重跑是全量的，复核是聚焦的——这两件事必须分开说，否则 CRA 的工作量会失控。

口径 3 · 已定

替换任何一份文件，全量重跑该 case 的所有专家规则。

原口径“只重跑被替换文件的规则”在存在跨文件规则时不成立—— 例如 booking fee 日期与 HP agreement 上 hirer 日期的比对，它同时引用两份文件。 按局部重跑会漏判，这是合规风险，不是体验问题。

但重跑全量，不等于让 CRA 把所有规则重勾一遍。 两者是两个概念，落到界面上要拆开：

  • 系统动作 · 全量、异步。 任一文件版本变更即触发整案专家规则重跑，结果回来前页面显示重算中。
  • CRA 复核范围 · 默认聚焦。 默认只呈现两类：本轮结论发生变化的规则，以及与新文件关联的规则。 其余保持既有结论，折叠展示、可展开查看。
  • 被跨文件规则牵动的“意外失败”，必须进 CRA 视野。 一条原本已通过的规则，因为另一份文件被替换而在重跑后转为 fail—— 这正是全量重跑的价值所在，它不能被折叠掉。

由口径 3 新推导出的一处细节（会上未讨论）。 跨文件规则重跑后失败时，defect 挂哪份文件？建议挂本轮被替换的那份文件： 它是变化的来源，也是 Sales 在下一轮唯一能动的东西。 若挂到另一份未被替换的文件上，Sales 会收到一条“文件没动却出了问题”的缺陷， 而系统并不允许他在这条 defect 里替换那份文件。此处需你确认。

两个页面在两轮里的动作是对称的：

“我不想区分这几个场景……我就按照最新的出来的那一波规则，一把给它缩回去。” 张骏 · 关于第二轮为什么一律用 update

“a 规则解掉了”有一个明确的判据：新文件上没有 alert、没有 fail。 在这个判据下，四种场景是这样收敛的—— c 与 d 一律走“原 defect 更新”，不做失效 + 新建（口径 1）：

更新时只动 type，不覆盖 remark。category 一定不变； defect type 集合由系统按最新规则自动改写； CR remark 里有客户自己写的内容，只能追加，不能覆盖。 这是保住人工判断留痕的唯一办法——也正是“删旧建新”方案最大的代价。

07

另一条线：Add Defect，先有缺陷后有文件

时序与前面完全相反，因此规则也相反：这条线上不跑专家规则。

  1. CRA · 工作台 手工新增 defect

    此时没有任何文件信息。这条 defect 不来自任何规则命中， 是 CRA 凭经验登记的。

  2. SALES 上传文件

    不限制 file type（因为没有规则可限）； 禁止上传到 OCR，只能进 file list（口径 7）。 这类文件不在专家规则范围内，走 OCR 会污染反显字段。

  3. CRA 人眼复核，勾选状态

    没有自动刷新、没有自动更新。整条线纯人工。

界面上怎么讲这条限制。 对 Sales 来说这是一个“同样是上传，为什么这次不能用 AI”的差异， 必须在入口处就说清楚，而不是等他点了才报错。AI 入口置灰并附一句：

This defect is not linked to a document type, so AI extraction cannot evaluate it. Upload the file directly to the file list.

因此 defect list 必须同时容纳两种来源： 系统创建的（可被系统自动修改）与人工创建的（只由人改）。 两者在列表里并存，来源需要可区分。

09

七条口径 · 已定稿

这七条原为待定项，现已全部拍板。以下是结论及其对方案的影响。

01

场景 c / d 的 defect 处置

取更新——原 defect 更新，不做失效 + 自动新建。

影响：CR remark 全程保住；不引入“一条 defect 关联多个文件 ID”的一对多关系； defect 状态机不需要新增“失效”态。第 06 节场景表按此重写。

02

第二轮 Manual Check 左侧规则栏

只展示该 file type 的规则，不通栏。

影响：Sales 与 CRA 在第二轮看到的是被收窄的视图； 全案影响由第 06 节的复核视图承接，不在这里展开。第 05、06 节按此定稿。

03

跨文件专家规则的重跑范围

替换一份文件时，重跑所有文件的规则。

影响最大的一条。它推翻了原口径“CRA 只复核与新文件相关的规则”， 需要 OCR 提供全案重跑接口，也要求复核视图区分“全量重跑”与“聚焦复核”。 并新带出一个待确认细节：跨文件规则失败时 defect 挂哪份文件（见第 06 节）。

04

反显取哪一份文件

取最新版本，且无未关闭 defect；否则不提供反显。

影响：不回退到旧版本，宁可不反显——数据宁缺毋滥。 交互上要有明确提示，告诉用户这组字段为什么是空的、需要先关掉哪条 defect。

05

删除的级联范围

CDM 删除主文件时，OCR 的子文件关联删除。

影响：避免“规则挂在一个已不存在的文件上”。 级联要一路清到规则结论与 defect 关联，否则会留下悬挂引用。 删除仍是客户手动动作、结果自负，系统只保证两侧一致。

06

defect type 的选择方式

改为多选。

影响：这是“一条 defect = 一份文件的一组问题”这条锚点的落地字段， 也是场景 c / d 自动更新的前提。生产上“选一个 type + remark 写其余”的将就做法可以退休。

外部依赖 · defect code 表由 ye 提供，需确认支持多选
07

Add Defect 线的上传方式

禁止走 OCR，只能进 file list。

影响：这条线上不跑专家规则、不反显、不自动更新，全人工。 界面上 AI 入口置灰并给出说明文案（见第 07 节），不能等用户点了才报错。

10

交互要点 · 按界面

上面的口径落到具体页面上是什么样。这一节是改原型时的清单。

CRA · 文件中心

Cross Validation 详情页

  • 每条失败规则后面一个创建按钮，点开是 defect 弹框， 规则编号、category、type、命中说明全部带入，CRA 确认即可。
  • 创建后告警不消失。该行同时显示“告警”与“已登记 defect”两个标记， 但不显示 defect 号、不可点进 defect 明细——查询只在工作台。
  • 第二轮进入时按钮变为“更新”变更， 动作是把该文件最新一轮的规则结论一次性写回原 defect，不新建。
  • 同一份文件命中多条规则时，合并进同一条 defect， type 为多选集合，而不是生成多条。

CRA · 文件中心

Manual Check 结果页

  • 第一轮：左侧通栏展示本 case 全部专家规则，右侧切换文件，逐条勾选； 顶部一个一键通过（全局），文件级别可创建 defect。
  • 第二轮：左侧只展示该 defect 关联 file type 的规则口径 2， 已通过的其他规则不展示；右侧看新上传文件的原文；顶部按钮为一键通过 + 更新 defect。
  • 一次进入若牵涉两条 defect，允许两条一起 rectify。
  • 系统文档（system-generated）走同一条人工判定路径，不做特例。

SALES · 文件中心（从 defect 进入）

收窄视图 · 定向重传

  • 只展示这条 defect 关联的文件，不是全量文件中心。
  • 上传区两个入口都开放（AI / 非 AI）， 但文件类型固定为 defect 关联的 file type，置灰不可改。
  • 上传成功后新文件生效，defect 一键关联到新文件， 旧文件与旧子文件原样留在页面上，不置灰、不隐藏、不自动删除。
  • 提示语要写明后果：删除是手动动作、结果自负。
  • OCR 分类与目标类型冲突时返回 others，页面上要能看出“这次没识别成功”， 并引导更换文件，而不是让他以为传成功了。
  • 两个 file type 有问题就是两条 defect，各自传一次，界面上不要试图合并。

CRA · 工作台

复核视图与 Defect List

  • 重跑是全量的，展示是聚焦的口径 3： 默认呈现“本轮结论发生变化的规则”与“新文件关联的规则”，其余折叠可展开。
  • 被跨文件规则牵动而转为失败的规则，必须单独提示， 不能混在折叠区里——它是全量重跑唯一的价值来源。
  • 重跑期间显示重算中状态，结果异步回来后刷新。
  • Defect List 区分系统来源与人工来源；系统来源可被自动改写，人工来源只由人改。
  • CRA 在文件中心确认过之后，提交时对应 defect 自动 verify， 不需要回到列表再点一遍。
  • defect 行上带关联文件信息，指向文件中心里那份文件。

CRA / SALES

Add Defect 独立线

  • CRA 手工新增时不带任何文件信息，category / type / remark 纯手填。
  • Sales 处理时不限制 file type，但 AI 入口置灰口径 7， 附说明文案，只能上传到 file list。
  • 这条线上没有规则、没有自动更新、没有反显，CRA 人眼复核后手工勾选状态。

CDM · 数据维护

Sync from OCR

  • 反显取该 file type 下最新版本、且无未关闭 defect 的文件口径 4。
  • 两个条件任一不满足，这组字段不反显，也不回退到旧版本取值。
  • 不反显时要给出可执行的原因，而不是留一片空白： 指明是哪条 defect 挡住了，关掉它字段就会回来。
  • 每次点击 Sync 时重新校验一遍文件与 defect 的关联关系，不用缓存结论。
