缺陷与文件的对齐

三场会真正在争的只有一件事：defect 到底挂在什么东西上。 维度定错，后面每一步——重传、重跑、复核、反显——都要靠特例去圆。 第三场末尾把它定在了文件 ID上，绝大多数争议随即消解。

01

现有流程：Batch 2 今天是怎么跑的

这是我们要改的起点，先把它说准，否则很容易改掉一个其实并不存在的问题。

  1. CRA · 工作台 登记 defect

    选 defect category，再选一个 defect type，写 CR remark。 登记时不记录关联哪份文件——现有 defect 结构里没有“关联文件”这个说法。

  2. CRA 退回给 Sales

    案件回到 Sales 手上，Sales 看到的是一条条 defect。

  3. SALES · 从 defect 入口进文件中心 上传新文件

    此刻文件中心是空的：申请阶段、放款阶段已存的文件他一份都看不到。 相当于为这条 defect 单开了一个文件中心，各 defect 之间互相隔离—— 从这个入口传上去的文件，也只在这个入口里能看到。

  4. SALES rectify 这条 defect

    上传和 rectify 是两个独立动作，Sales 要各做一遍。

  5. CRA · defect list verify

    在 defect 列表里直接确认，不需要回文件中心看文件。

生产上的实际做法，比设计更宽松。一份文件常常一次命中多条规则， 但 defect type 现在是单选。CRA 的做法是：选完 category，随便选一个 type， 把其余问题全部写进 CR remark。也就是说——

生产里的一条 defect，事实上已经等于“一份文件的一堆问题”， 而不是“一条规则的一个问题”。我们要做的不是发明新维度，是把这个既成事实变成系统里的显式结构。

口径来源：与张浩确认 defect rules 表（字段定义、defect category number、defect id number 均由 ye 方提供）； defect type 改多选张浩认为是“万一想要”的能力，需 ye 侧最终确认。

02

核心挑战：七个难点，按“为什么难”排

这七条是三场会反复回到的地方。前四条是结构性的，后三条是它们的衍生。

  • 难点一 · OCR 里其实有两类规则，但只有一类该产生 defect。 一类是 OCR 自己的文件校验规则（为了保证提取准确、供下游反显）， 另一类是配进 OCR 的专家规则。只有后者不过才值得登记缺陷； 前者不过只说明“这份文件读不准”。两类混在同一个告警区里，是 CRA 反复困惑的直接来源。
  • 难点二 · 告警清零与缺陷留存互相冲突。 CDM 的现行逻辑是：所有告警处理完，数据才落库，下游才能反显。 但我们想要的是“创建了 defect，告警仍然保留”——不然缺陷的证据就没了。 这两条规则今天不能同时成立。
  • 难点三 · defect 挂在哪个维度上，一直没定。 挂规则？一份文件命中五条规则就是五条 defect，CRA 要处理五遍，与生产实际相反。 挂 file type？同一 type 下可能有多份文件，第二轮又会新增一份，指代不清。 挂主文件？OCR 会把一个 PDF 拆成多个子文件，主文件层面已经无法区分是哪一部分出的问题。
  • 难点四 · OCR 与非 OCR 的层级根本不对齐。 OCR 有“主文件 → 子文件”两层，非 OCR 只有主文件一层，而专家规则是跟着 file type 跑的。 会上明确说过“非 OCR 你怎么拆——让用户上传时自己拆，对他要求太高了”。 两条路径不在同一维度，任何关联规则都要写两套。
  • 难点五 · 第二轮重传要不要走 OCR，两边都有代价。 走 OCR：能重新提取、能反显、规则能自动重判；代价是必须限死文件类型， 且分类识别可能和目标类型冲突。不走 OCR：文件干净地进 file list， 但 OCR 侧的数字永远不更新，规则只能靠人工断言。
  • 难点六 · 新文件上来之后，旧 defect 和旧文件怎么处置。 旧 defect 删掉，CRA 手写的 remark 就丢了；保留，列表里就会积压已经不成立的条目； 旧文件如果系统自动置为失效，等于一次隐性删除—— “我不知道客户同不同意这么干。”
  • 难点七 · 两边各操作一遍，是最贵的成本。 文件中心处理一遍告警、defect 那边再处理一遍状态，同一件事做两次。
“他既要在这边操作一遍，又要在 OCR 操作一遍，又要在 defect 那边再操作一遍。我觉得是最差的方案。” 张骏 · 09-04 上午场

会上还认真推演过一个更激进的方案：干脆不要 defect，改成一份 log。 结论是不成立——log 只记录“哪一条被替换掉了”， 但“新文件到底有没有解掉 a 规则、谁来判”这个问题它一个字都没回答。 缺陷之所以贵，正是因为它承载了责任人和结论，这部分不能省。

03

解决方案 · 第一步：把维度定死

这是第三场会最重要的产出，也是后面所有交互的地基。

Anchor

defect 关联的是文件 ID，不是规则，也不是 file type。
一条 defect = 一份文件的一组问题。

file type 决定跑哪些专家规则；专家规则命中在具体的文件 ID 上； defect ID 与 file ID 一一对应。文件 ID 比 file type 承载更多信息， 也能区分同一类型的多个版本——这正是第二轮重传所需要的。

一个主文件里的两个 file type 都有问题，就是两条 defect。 对应地，Sales 退回后要传两次、rectify 两次——这不是设计的粗糙， 而是因为第二轮必须按 file type 锁定重传，两个类型无法合并成一次上传。

04

解决方案 · 第一轮：在文件中心创建，告警不清

缺陷的唯一发源地是文件中心；缺陷的唯一查询地是 CRA 工作台。两者不重叠。

  • 创建入口在文件中心，手动触发。 Cross Validation 详情页与 Manual Check 结果页各提供一个创建按钮， 弹出 defect 弹框，把失败规则的内容快速带入，CRA 确认后落库。
  • 创建后，对应的规则告警保留。 这是本轮设计与现状最大的一处冲突： OCR 需要具备“带告警保存”的能力，否则 CDM 不落库、下游反显拿不到数据。 这是必须提给 OCR 侧的改动。
  • 文件中心不提供查看 defect 的能力。 不建 defect tab、不显示 defect 明细。所有 defect 查询集中在 CRA 工作台， 避免同一份台账出现两个入口、两套数字。
  • Manual Check 结果页提供“一键通过”（全局）， 与文件级别的创建 defect 并列。第一轮的动作是创建。
  • 人工上传第一轮可确定一个或多个 file type。 左侧通栏展示这个 case 涉及的全部专家规则，右侧是不同的文件，CRA 逐条勾选。
05

解决方案 · 第二轮：锁定文件类型的定向重传

Sales 从 defect 进入文件中心，看到的是一个被收窄过的世界。

Sales 侧 · 从 defect 入口

  • 仅展示关联文件，不是全量文件中心。
  • 可上传新文件，OCR 与非 OCR 两个入口都开放。
  • 文件类型被 defect 锁死，不可选——它就是这条 defect 关联的 file type。
  • 上传成功后新文件生效，defect 一键关联到新文件。
  • 两个 file type 有问题就传两次、rectify 两次。

系统不做的事

  • 不自动删除旧文件，OCR 与 manual 的原文件、子文件全部留在页面上。
  • 不自动把旧文件置为失效——那是一次隐性删除。
  • 客户可以手动删除，结果自负。
  • 传错文件也不做处理，只按原样预览。

OCR 侧的处理口径。第二轮仍走 OCR 的好处是能继续反显； 代价是必须限制文件类型。为此单独设置提示词：只能选目标 file type； 若分类识别与目标文件冲突，OCR 统一输出为 others，不识别、不提取。 传错文件、目标文件缺失，同样输出 others。Sales 通过更换文件自行解决。

Manual Check 侧的展示口径。左侧只展示这条 defect 所关联 file type 的规则， 屏蔽掉其他已经通过的规则；右侧看新上传文件的原文。 同一次进入若牵涉两条 defect，可以两条一起 rectify。 （左侧究竟只展示该 file type 的规则、还是通栏展示全部——见第 09 节待定第 2 条。）

06

解决方案 · CRA 复核与四种结果

第一轮 create，第二轮 update；verify 是自动的，因为 CRA 已经在文件中心看过了。

两个页面在两轮里的动作是对称的：

“我不想区分这几个场景……我就按照最新的出来的那一波规则，一把给它缩回去。” 张骏 · 关于第二轮为什么一律用 update

“a 规则解掉了”有一个明确的判据：新文件上没有 alert、没有 fail。 在这个判据下，四种场景是这样收敛的：

更新时只动 type，不覆盖 remark。category 一定不变； defect type 若改为多选，则由系统自动更新 type 集合； CR remark 里有客户自己写的内容，只能追加，不能覆盖。 这是保住人工判断留痕的唯一办法——也正是“删旧建新”方案最大的代价。

07

另一条线：Add Defect，先有缺陷后有文件

时序与前面完全相反，因此规则也相反：这条线上不跑专家规则。

  1. CRA · 工作台 手工新增 defect

    此时没有任何文件信息。这条 defect 不来自任何规则命中， 是 CRA 凭经验登记的。

  2. SALES 上传文件

    不限制 file type（因为没有规则可限）； 禁止上传到 OCR，只能进 file list。 原因是这类文件不在专家规则范围内，走 OCR 会让反显出问题——这一点要向客户讲清楚。

  3. CRA 人眼复核，勾选状态

    没有自动刷新、没有自动更新。整条线纯人工。

因此 defect list 必须同时容纳两种来源： 系统创建的（可被系统自动修改）与人工创建的（只由人改）。 两者在列表里并存，来源需要可区分。

这一节是给开发估工作量看的，也是提给 OCR / CDM 两侧的改动清单。

09

待定：七个问号

下面每一条，会上都出现过两种或以上的说法，且没有收敛。写需求前需要各定一个。

1

场景 c / d：原 defect 更新，还是原 defect 失效 + 自动新建？

会上最后倾向直接更新（“不会删一个旧的、创建一个新的”）， 理由是 remark 不丢；但也说过失效 + 新增工作量更小。 失效方案会引入“一条 defect 关联多个文件 ID”的一对多关系， 且 defect 现有状态机里只有 rectify / verify，没有“失效”这个态—— 若要留痕就只能标成 verify，语义不对。建议取更新。

2

第二轮 Manual Check 左侧：只展示该 file type 的规则，还是通栏展示全部？

张骏明确表态“只展示 file type 比较好”； 但也提过一种更省事的处理——从任一 defect 进去都展示相关的全部规则，右边只切文件。 本文暂按“只展示该 file type”撰写，若改口径，第 05 节要跟着改。

3

跨文件的专家规则，替换一份文件时要重跑哪些？

当前口径是“只重跑被替换文件的规则，其他文件的规则不动”， 这在存在跨文件规则时不成立——例如 booking fee 日期与 HP agreement 上 hirer 日期的比对， 它同时引用两份文件。需要明确：替换一份文件时，是否重跑所有引用了该文件的规则。 这是会上被简化假设掉、但真实存在的一类。

4

旧文件保留不动，反显取哪一份？

“系统不做自动处理、旧文件原样留着”与“反显必须有唯一数据源”是冲突的。 同一 file type 下会同时存在新旧两份文件， 需要定：反显固定取最新版本，还是取没有关联未关闭 defect 的那一份。

5

CDM 删除主文件时，OCR 的子文件是否级联删除？

会上提出但未答。两边不同步会直接造成“规则挂在一个已不存在的文件上”。 需要与 OCR 侧确认接口是否支持。

6

defect type 改多选，ye 侧是否接受？

张浩认为是“万一想要”的能力，但 defect category / type / code 表由 ye 提供。 多选是本方案“一条 defect = 一份文件的一组问题”的前提， 若不能多选，就只能退回“选一个 type + remark 写其余”的现状做法， 场景 c / d 的自动更新也就无处落。这条优先级最高。

7

Add Defect 线禁止走 OCR，如何向客户交代？

技术理由是避免反显出错，但对 Sales 来说这是一个“同样是上传，为什么这次不能用 AI”的差异。 需要一句能对外讲的说明，以及在界面上如何呈现这条限制。
