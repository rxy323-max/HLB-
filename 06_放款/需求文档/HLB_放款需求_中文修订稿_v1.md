## 1. 缺陷的锚定维度：从规则改为文件

### 1.1 FSD 原文

- **3.9.7 ①**："For one specific rule that is currently Failed, the user may manually create the corresponding Defect record."
- **12.7.7**：去重键为 **Rule ID + File Owner / Entity**，理由是同一 Rule ID 可能出现在不同主体（主申请人 / 担保人 1 / 担保人 2）的同类文件上。
- **12.7.4**：Type 为单选下拉（Drop list）。

即：**一条失败规则 → 一条缺陷**。

### 1.2 会议调整

三场会议反复推演后确认，按规则建缺陷在真实业务里走不通：

1. **一份文件通常同时命中多条规则**。HP Agreement 同时"签署日期超期"和"末页缺见证日期"，按规则会生成两条缺陷，Sales 却只需要重传一次。生产上 CRA 现在的将就做法就是"选一个 type，其余写进 remark"——正说明单条规则的粒度不对。
2. **Sales 的动作单位是文件**。打回后 Sales 能做的只有"重传这份文件"，缺陷若挂在规则上，Sales 无法判断要传几份、传哪份。
3. **重传后规则集会变**。原来失败的规则可能通过、新的规则可能失败（见第 5 节四种结果）。缺陷若锚在规则上，就必须"作废旧缺陷 + 新建缺陷"，CRA 写过的 remark 全部丢失；锚在文件上则只需更新。
4. **跨文件规则无法归属**。一条规则同时读两份文件，锚在规则上就无法回答"该重传哪一份"。

### 1.3 修订后口径

**一份文件 = 一条缺陷，承载该文件当前全部失败规则。**

| 项 | 修订后 |
|---|---|
| 锚点 | 文件 ID（OCR 拆分出的子文件各自独立成缺陷） |
| 去重键 | **文件 ID**（文件 ID 天然唯一确定主体与文件类型，涵盖 FSD 12.7.7 "Rule ID + Entity"的去重目的且更稳定） |
| 缺陷类型 | 多选，取该文件所有失败规则映射出的 Defect Type 之集合（见第 3 节） |
| 缺陷分类 | 取该文件首条失败规则映射出的 Defect Category |
| CRA 备注 | 只追加不覆盖，历次更新记录保留 |
| Rule–Defect Mapping | **保留**。它仍是"失败规则 → Defect Code / Category"的转换依据，只是转换结果汇入文件级缺陷，而非各自成条 |

**非 OCR 文件的对齐**：Manual Check 页面的文件同样以文件 ID 为锚点。对于没有经过 OCR 拆分的文件，以 CDM 侧的文件 ID 为准，使两条路径的缺陷结构一致。

**验收点**

1. 一份文件命中 3 条规则 → 缺陷列表只增加 1 条，Type 含 3 项。
2. 同一份文件重复点击创建 → 不新增，改为更新。
3. 主申请人与担保人各有一份 MyKad 且命中同一 Rule ID → 生成 2 条缺陷，互不影响。
4. 缺陷行显示其关联文件名，可跳转到文件中心中该文件。

## 2. OCR 规则分两类，只有专家规则产生缺陷

### 2.1 FSD 原文

**2.8.4**："The rules may include Eyeball Check, formula validation, consistency validation, and other applicable validation types." —— 未区分规则性质。
**3.9.5**：所有未处理的告警一律视为 Failed，可记为缺陷。

### 2.2 会议调整

OCR 引擎实际同时输出两类结果：

| 类别 | 回答的问题 | 举例 | 打回 Sales 能解决吗 |
|---|---|---|---|
| **专家规则** | 这笔案子是否合规 | 保额低于要求、签署日期超期、发票日期早于申请日期 | 能——换一份正确的文件 |
| **OCR 自校验** | 这份文件是否读得清楚 | 某字段未抽取到、页面倾斜导致置信度偏低 | **不能**——重传同一份文件，结果一样 |

把两者混在一起，会把"识别质量问题"当成"文件问题"退给 Sales，造成无效往返。

### 2.3 修订后口径

1. **规则配置侧**：专家规则清单（CDM 侧 Rule–Defect Mapping 表）中，只有登记了 Defect Code 的规则才可产生缺陷；OCR 自校验规则不进入该表，因此天然不可产生缺陷。建议在 OCR 规则清单上显式增加 `rule_class` 标识（`EXPERT` / `SELF_CHECK`），避免依赖"有没有配 Defect Code"这种隐式判断。
2. **界面侧**：Cross Validation 详情页把告警分**两个独立区块**展示，不是两个小标题：
   - 专家规则告警：带创建 / 更新缺陷按钮；
   - OCR 自校验：无创建按钮，仅可 Justification 或更换文件，区块内注明"本组不产生缺陷"。
3. **计数侧**：两类数字**不相加**。文件状态列分别显示 `Alert n`（专家规则）与 `QC n`（自校验）；页签的异常计数、"有问题的文件"判定只统计专家规则。仅剩自校验未处理的文件不计为异常文件。

**验收点**：一份文件有 2 条专家规则失败 + 1 条自校验待处理 → 文件状态显示 `Alert 2` 与 `QC 1` 两个标签；创建缺陷时带入的规则只有 2 条；自校验那条不出现在缺陷内容里。

## 3. 缺陷类型改为多选

### 3.1 FSD 原文

**12.7.4**：`Type | Defect Type | Drop list`（单选）。

### 3.2 会议调整

单选是"一条规则一条缺陷"的产物。改为文件维度后，一条缺陷必须能同时表达该文件的多个问题。

### 3.3 修订后口径

- Defect Type 改为**多选**，界面为可勾选的下拉框（保持下拉形态，不改成标签墙）。
- 创建时由系统按 Rule–Defect Mapping 预填该文件所有失败规则对应的 Type，CRA 可增删。
- 第二轮更新时，Type 集合按最新一轮规则结论**整体重写**，Category 不变，缺陷编号不变。

**外部依赖**：Defect Code 参数表（18.28）需确认支持一条缺陷挂多个 Type。若数据结构上无法支持多值，退而求其次的方案是主 Type + 附加 Type 列表，但需在评审中明确。

## 4. 告警与缺陷正交

### 4.1 FSD 原文

**3.9.5**："If the alert is retained without any action, the rule shall be treated as Failed and may subsequently be recorded as a Defect." —— 未说明创建缺陷后告警的去向。

### 4.2 会议调整

创建缺陷**不等于**处理了告警。两者回答不同问题：告警回答"这条规则现在是什么结论"，缺陷回答"这件事该谁去办"。若创建缺陷即清除告警，第二轮重跑时就失去了比对基准，也无法解释"这条缺陷当初是因为什么建的"。

### 4.3 修订后口径

1. 创建 / 更新缺陷后，**告警原样保留**，规则结论仍为 Failed。
2. 该告警行同时显示两个标记："告警"与"已登记缺陷"，但**不显示缺陷编号、不可点入缺陷明细**——缺陷的查询入口只在工作台的 Defect List，文件中心不承担第二份缺陷台账。
3. 规则结论转为 Passed 只有三条路径（沿用 FSD 3.9.5）：改值、Justification、换文件后重跑通过。

**外部依赖**：OCR 侧需支持"带未关闭告警保存"。当前实现要求告警全部处理才能保存，与本条冲突，需 OCR 团队确认改造。

## 5. 第二轮定向重传与四种复核结果

### 5.1 FSD 原文

**2.9** 规定了打回后 Sales 的权限边界（可新增、可替换、不可修改既有文件；不可操作规则页），但未规定第二轮重跑后缺陷本身如何演进。

### 5.2 会议调整

会上完整推演了 Sales 重传一份文件后的四种可能，并确认统一走"更新"而非"作废 + 新建"（口径 1）。

### 5.3 修订后口径

**Sales 侧 · 定向重传**

- 从缺陷行进入文件中心，视图收窄到该缺陷关联的那一份文件；提供"查看全案"退出收窄。
- 上传区两个入口都开放，但**文件类型固定为缺陷关联的类型，置灰不可改**。
- OCR 分类结果与目标类型冲突时返回 others、不抽取任何内容；页面必须显示"本次未识别成功"并引导更换文件，不可让 Sales 以为已传成功。
- 新版本生效后，旧版本**原样保留**在列表中，不置灰、不隐藏、不自动删除；删除是人工动作、后果自负。
- 一份主文件被 OCR 拆成两个都有问题的文件类型时，就是两条缺陷、**各自上传一次**，界面不做合并。

**重跑后的四种结果**

| 场景 | 规则结论 | 缺陷处置 |
|---|---|---|
| a | 原规则仍失败 | 缺陷维持原样，状态置为"已回传待复核" |
| b | 原规则全部通过 | 缺陷可关闭；CRA 提交时自动核验（见第 12 节） |
| c | 原规则通过，但新规则失败 | **更新**原缺陷：Type 集合重写、备注追加、编号与 Category 不变 |
| d | 部分通过 + 新增失败 | 同 c |

**跨文件规则的连带**

按 FSD 2.8.3，任一文件变更即全案重跑，因此可能出现"没被替换的文件上的规则翻转为失败"。该情形必须在复核视图中**单独提示**，不可混入折叠区——它是全量重跑唯一的价值来源。

> **待决**：此类缺陷挂在哪一份文件上。原型现实现为挂在**本轮被替换的文件**（理由：它是变化来源，且下一轮 Sales 只能动这一份）；另一选项是挂在规则实际命中的另一份文件。需确认。

## 6. 全量重跑 + 聚焦展示

### 6.1 FSD 原文

**2.8.3** 已明确：任一文件新增或替换 → 全案所有文件的规则重跑；不保留历史快照，只留最新结果。**与会议口径 3 一致，无需修改。**

### 6.2 会议补充

FSD 未规定重跑结果**如何呈现**。全案 20+ 条规则每次重传后全部重读，CRA 无法承受。

### 6.3 修订后口径

重跑是全量的，**展示是聚焦的**：

1. 默认呈现两类规则：本轮结论发生变化的、以及挂在本轮被替换文件上的；
2. 其余规则保留上一轮结论，折叠展示，可一键展开；
3. 因跨文件规则翻转的，单独醒目提示；
4. 重跑期间显示"重算中"状态，结果异步返回后刷新。

## 7. Manual Check：第二轮收窄与一键通过

### 7.1 FSD 原文

**3.9.4** 规定了列表页范围（非 OCR 且已指定文件类型）、详情页左右布局、以及混合上传 / 单独上传两种展示场景。未规定轮次差异，也未规定批量操作。

### 7.2 修订后口径（新增）

| 轮次 | 左侧规则栏 | 顶部操作 |
|---|---|---|
| **第一轮** | 通栏展示本案全部专家规则，右侧切换文件逐条勾选 | **一键通过（全局）** |
| **第二轮** | **只展示该缺陷关联文件类型的规则**（口径 2），已通过的其他规则不展示 | 一键通过 + 更新缺陷 |

补充要求：

- 创建 / 更新缺陷的入口设在**文件标题行**，而非只在某条失败规则上——缺陷锚在文件上，入口就应在文件上。
- 一次进入若牵涉两条缺陷，允许两条一起标记 Rectified。
- 系统生成文档（system-generated）走同一条人工判定路径，不做特例。
- 从文件标题直接创建、且该文件没有任何规则判失败时，缺陷来源记为 **User**（CRA 自行判断），不得冒充 System。

## 8. Sync from OCR 的反显门槛

### 8.1 FSD 原文

**3.9.6** 规定：弹窗比对 OCR 抽取值与页面现值，用户可选择性回填，回填后仍可编辑；反显范围含必备文件清单的勾选状态；与 Refresh Rule Results 完全解耦；Post Maintenance 之后不再提供；手写签署内容不参与反显。

### 8.2 会议调整（口径 4）

未规定"从哪一份文件取值"。若从旧版本或从仍有未关闭缺陷的文件取值，等于把已知有问题的数据写进正式字段。

### 8.3 修订后口径

1. 反显取该文件类型下**最新版本**、且该文件**无未关闭缺陷**的文件。
2. 两个条件任一不满足，**该组字段不反显**，也不回退到旧版本取值——数据宁缺毋滥。
3. 不反显时必须给出可执行的原因：**指明是哪一条缺陷挡住了**，关闭后字段即可回填；不可只留空白。
4. 每次点击 Sync 重新校验文件与缺陷的关联关系，不使用缓存结论。

## 9. Add Defect 独立线

### 9.1 FSD 原文

**12.7.6 ①**：用户可在 Defect List 中手工创建**不关联任何规则**的缺陷。
**12.7.4 Action**：缺陷行提供 Upload（上传文件并绑定到该缺陷）。

### 9.2 会议调整（口径 7）

这条线上没有文件类型信息，AI 无从比对——若允许走 OCR 入口，只会得到 others 与空抽取，浪费一次往返。

### 9.3 修订后口径

- CRA 手工创建时**不带任何文件信息**，Category / Type / 备注纯手填，来源记为 User。
- Sales 处理这条缺陷时**不限制文件类型**，但 **AI 入口置灰并给出说明文案**，只能上传到 file list。置灰是事前提示，不能等用户点了再报错。
- 这条线上没有规则、不触发重跑、不参与反显；CRA 人眼复核后手工勾选状态。

## 10. 删除的级联范围

### 10.1 FSD 原文

**2.7.7**：删除只能在 File List 操作，进入 Deleted Files 列表，不可预览、不可恢复。
**2.7.3**：删除担保人时，其名下文件一并移入 Deleted Files。

### 10.2 修订后口径（新增，口径 5）

CDM 侧删除主文件时，**OCR 侧拆分出的子文件级联删除**，并一路清理：

1. 挂在这些子文件上的规则结论；
2. 指向这些文件的缺陷关联（缺陷本身不自动删除，但需标记"关联文件已删除，请针对新文件重开"）。

目的是避免出现"规则挂在一个已不存在的文件上"的悬挂引用。删除仍是人工动作、后果由客户承担，系统只保证两侧一致。

## 11. Header Summary

### 11.1 FSD 原文（3.9.2）

应显示：① 本案必备文件数与已上传数；② 适用规则总数；③ 已有结论的规则数；④ 已结论中 Passed / Failed 各多少；⑤ 可展开查看明细；⑥ 提供直达文件中心的快捷链接；⑦ 失败规则提供 Create Defect 按钮，点击后才生成；⑧ Refresh 不创建、不覆盖、不更新缺陷；⑨ 显示最近刷新 / 保存时间，只显示时间不显示操作人。

### 11.2 会议调整

FSD 规定的六项数字**全部保留**。需要调整的是分层与展开后的结构：

| 调整点 | 说明 |
|---|---|
| **展开明细按文件维度** | 一份文件一张卡片，卡头是文件名、该文件未通过条数，以及**唯一**的创建 / 更新缺陷入口；规则行退回卡片内部，只保留处理规则（改值 / Justification / 换文件）。这与第 1 节的锚点一致 |
| **Passed 的构成** | 按 FSD 3.9.5，Passed 包含"真通过 / Justification 放行 / 人工标记通过"三类。三类的责任完全不同，建议在 Passed 下以小字显示构成——靠 Justification 放行的部分是 CRA 签字承担的风险 |
| **未登记缺陷数** | "Failed 中尚有 N 条未登记缺陷"应显示在卡片上，并就近提供批量创建入口（FSD 3.9.7 ②），而非仅在展开后才能看到 |
| **必备文件的自动回写** | FSD 3.9.6 允许 Sync 范围包含必备文件清单勾选状态。建议在该数字下注明"其中 N 项由规则全通过自动回写"，这是 OCR 接入后 CRA 手工量下降最直观的体现 |

**明确不纳入 Header Summary**：缺陷的 Rectified / Verified 闭环状态。依据 FSD 3.9.7"Defect List 与 Header Summary 完全解耦"，闭环状态属于 Defect List。

## 12. 缺陷自动核验

### 12.1 FSD 原文

**12.7.5**：Mark as Verified 为 CRA 手工操作。

### 12.2 会议调整

场景 b（重传后该文件规则全部通过）下，CRA 已经在文件中心逐条确认过结论，回到列表再点一次 Verified 属于重复劳动。

### 12.3 修订后口径

- 满足全部条件时，缺陷在 CRA 提交时**自动置为 Verified**：来源 = System、关联文件的全部专家规则均为 Passed、且该缺陷已被 Sales 标记 Rectified。
- 来源 = User 的缺陷**不参与**自动核验，一律人工。
- 自动核验须在缺陷备注中留痕（"规则于第 N 轮全部通过，提交时自动核验"），保证可审计。
