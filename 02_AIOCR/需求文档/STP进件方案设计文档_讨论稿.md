# STP 进件方案设计文档（讨论稿）

> 用途：团队内部讨论 — 评估方案对现有系统的改动量与可实现性
> 范围：STP 进件路由方案。质检（OCR 内部功能）为独立需求，不在本文范围，仅作为信号来源被引用
> 日期：2026-06-10

---

## 一、目标（Why）

### 1.1 业务目标

**提高 STP rate** — 这是 Sales 和 CED 之间唯一的共识。

### 1.2 客户原话归纳

> "在合规前提下，给销售侧足够的流程灵活性，同时保障风控逻辑的严谨性。"

拆解为四个层面：

| # | 客户需求 | 含义 |
|---|---------|------|
| 1 | 双路径可选的审核流程 | 材料无硬伤可直进 STP；有问题或 Sales 没精力处理，可转 CED 人工，两条路按需选 |
| 2 | OCR 环节的弹性安排 | 不强制 Sales 必须自己处理 OCR，CED 也可承接；「OCR 材料完整性」是路由的核心判断依据之一，不限定执行角色 |
| 3 | 风控规则的统一与闭环 | 所有路由决策由统一风险引擎做（现有风控规则 + 新增 OCR 完整性规则），杜绝"绕开风控直接进人工"的逻辑漏洞 |
| 4 | 落地可操作性 | 不推翻现有流程，先解决核心卡点（提交节点判断逻辑、流程监控、规则文档化），最小可用方案起步，逐步迭代 |

### 1.3 现状痛点

- Sales 不愿承担规则审核责任，提交材料质量参差，残缺案件涌入流程
- STP 率统计口径失真：残缺提交被计入分母，表面数字偏低且无法定位责任
- Sales 与 CED 互相博弈：Sales 觉得复核是额外负担，CED 觉得在被动承接 Sales 的活

---

## 二、核心设计理念（What）

### 2.1 一句话方案

> **把"OCR 完整性"从前置关卡改为路由信号：Sales 随时可提交，材料质量决定案件走哪条路，而不是决定 Sales 能不能提交。**

设计语言的转变：从"规则触发拦截"改为"**置信度驱动路由**"。

### 2.2 关键原则

**原则 1：引擎是唯一路由点**
Sales 端、CED 端都不做路由判断，只产生信号。进人工本身也是引擎的输出之一，不存在旁路。

**原则 2：Sales 复核 → STP 置信度更高（已确认成立）**
OCR 是概率产品，误差来自文件质量与 AI 判断偏差两个来源。Sales 对照原件确认分类与字段，等于给 OCR 结果加一层人工背书。同一份文件：
- 未复核的 OCR 结果 → 置信度 = AI 模型输出
- Sales 确认过的结果 → 置信度 = AI 输出 × 人工核实

后者进入引擎触发误判警报的概率更低，STP 被意外拦截的概率也更低。

**原则 3：复核从"义务"变为"利益可见"**
不强制 Sales 复核，但让他实时看到复核对路由结果的影响 — 想快就复核走 STP 快车道，不想管就交给 CED，选择权和后果都在 Sales。

**原则 4：CED 交互保持轻量**
CED 任务只有三个状态（待处理 → 处理中 → 已完成）、三个动作（Resolve / Return / Override→Manual）。CED 清完规则即放手，案件回引擎重判，CED 不接管整单。

### 2.3 与质检需求的边界

| | 质检 | STP 进件 |
|---|------|---------|
| 定位 | OCR 内部功能 | 联动单文件 OCR + 进件其他信息 + 多文件交叉校验后的整体路由 |
| 输出 | 单文件质量信号（模糊/属主等）| 案件级路由决策 |
| 关系 | 质检结果是 STP 路由的**信号来源之一** | 消费质检与其他所有信号 |

## 三、方案设计（How）

### 3.1 提交后三路径路由

Sales 上传录入不设限制，Submit 后由引擎按最严重信号路由：

| # | 触发规则类型 | 后续流向 | 说明 |
|---|------------|---------|------|
| ① | 没有告警 | 进入 STP | 全自动直通，无拦截 |
| ② | 告警规则 | 进入 STP（带引擎标记）| 告警随单进入审批记录，供审批中处理 |
| ③ | 拒绝规则 | 进入 CED 清规则 | 硬拦截，CED 完成规则清理后回引擎重判 |
| ④ | OCR 未完成 | 进入 CED 代处理队列 | 对应客户需求 2 的弹性：CED 承接分类确认/字段核对 |

> ⚠️ 待确认：路径②"带标记进 STP"的语义需与客户三选一 —
> a. 引擎自行消化（告警仅作为风险因子，真 STP）
> b. 条件批准（先批，放款前由 CRA/CED 清告警）
> c. 并行处理（STP 与 CED 清告警同时进行，需定义清不掉的回退逻辑）

### 3.2 前台流程（Sales 侧）

```
阶段A 上传与录入（无门槛）
  · 上传文件 → 质检结果实时回显
  · OCR 分类确认、字段复核 → 可做可不做
  · 常驻「STP 就绪度面板」：
      材料完整度  8/10
      OCR 复核    5/7 已确认
      材料侧预检  1 项告警
      → 当前提交预计路径：CED 协助处理
      → 补齐后预计路径：STP 直通
        ↓ 任意时刻可 Submit
阶段B 提交确认（预检结果摊牌）
  「您有 2 份文件未复核，提交后将由 CED 协助处理，
    预计增加 1 个工作日。」 [返回补齐] [确认提交]
        ↓
阶段C 提交后跟踪（只读）
  审批中（STP）/ CED 处理中 / 已退回（附 Defect Note）
```

**就绪度面板的架构定位（关键澄清）**：
前端不做任何规则判断。面板数据来自调用风险引擎的**预检接口（pre-check，试算模式）** — 同一套规则、同一个引擎，只是提交前以无副作用方式跑一遍。预检仅覆盖材料侧规则（完整性、OCR 冲突、文件质量）；CCRIS/CTOS/AML 等征信合规检查只在正式提交后执行，界面上须明确表述：

> "材料侧检查：预计通过 ✓。征信与合规检查将在提交后进行。"

不承诺"必进 STP"，不越权替引擎打包票。

### 3.3 后台流程（引擎 + CED 侧）

```
Submit
  ↓
风险引擎（一次性全量）：
  完整性 / 重复 / 资格 / OCR冲突 / 质检置信度
  + CCRIS / CTOS / AML / 反欺诈 / DSR
  ↓ Route Decision（沿用现有节点）
  ├─ 全过        → STP → Auto Credit Approved
  ├─ 仅 Warning  → STP 继续，告警随单
  ├─ 材料类异常   → CED 任务队列（带任务标签）
  ├─ 欺诈疑点     → FMU（不变）
  └─ 政策硬伤     → Reject（不变）
  ↓
CED 处理（仅材料类异常）：
  Resolve（填 justification）/ Return（生成 Defect Note）/ Override→Manual
  ↓ Resolve 后
回引擎重判（CED 不直接放行）
  ├─ 全过 → 继续 STP
  └─ 仍有问题 → 再循环或转人工
```

CED 任务卡上用标签区分两类任务（不增加状态机复杂度）：
- **规则异常**：Sales 已完成 OCR，硬规则挂起，CED 决定放行或退回
- **OCR 待确认**：Sales 未完成 OCR，CED 承接（界面与 Sales 复核页一致）

### 3.4 指标体系（解决口径失真）

| 指标 | 公式 | 属主 | 频率 | 回答的问题 |
|------|------|------|------|----------|
| **有效提交率** | 通过完整性校验的提交 / Sales 总提交 | Sales | 日/周 | 材料提交质量 |
| 引擎直通率 | 引擎判 STP / 有效提交 | 规则/风控团队 | 周/月 | 规则是否合理 |
| 引擎告警穿透率 | 仅 Warning 仍进 STP / 引擎判 STP | 规则/风控团队 | 月 | 告警规则是否是噪音 |
| STP 审批通过率 | Auto Credit Approved / 进入 STP | 信审/CED | 月/季 | STP 风险标定准确度 |
| CED 协助直通率 | CED 清规则后回引擎判 STP / CED 处理的材料类任务 | CED 团队 | 周 | CED 对 STP 的正贡献 vs 被动承接 |

**当前阶段关注重点：有效提交率。**
口径失真的根源是分母不干净 — 残缺提交被计入 STP 计算。把有效提交率单独拎出，Sales 行为质量与引擎判断质量即分离。该指标也是 Sales 最易接受的：它衡量"材料够不够格进系统"，而非"客户有没有通过审批"。

**口径建议**：区分**纯 STP rate**（零人工触碰）与**辅助直通率**（CED 仅清规则、未做信审判断）。Sales 的努力体现在前者，CED 的效率体现在后者，各有成绩单，消解冲突。

**对外口径建议**：口径对齐前不对外公布单一"STP 率"数字，先在内部以漏斗图呈现五个指标的关系，各方认可自己负责的一层后，再在管理层合并对外口径。

## 四、改动量评估（团队讨论重点）

### 4.1 对现有系统的改动清单

| 模块 | 改动 | 改动量评估 |
|------|------|----------|
| 风险引擎 | 新增 OCR 完整性规则组；新增 pre-check 试算接口（无副作用模式）| **中** — 规则框架沿用，主要是新规则录入 + 一个只读接口 |
| Route Decision | 现有节点不变，新增"材料类异常 → CED 队列"与"OCR 未完成 → CED 代处理"两个出口 | **小** — 在现有路由表上加分支 |
| Sales 前端 | 新增就绪度面板、提交确认页、提交后跟踪视图 | **中** — 纯展示层，无规则逻辑 |
| CED 工作台 | 任务卡加类型标签；三动作（Resolve/Return/Override）| **小** — 现有审核界面收敛而非扩展 |
| OCR/质检 | 无改动（独立需求）— 仅要求其输出信号可被引擎消费 | **小** — 接口约定 |
| 报表 | 新增五指标漏斗 | **中** — 取决于现有数仓 |

### 4.2 不改的部分（符合客户需求 4）

- 现有 System Review / Pre-screen → Hard Rules → Risk Checks → Route Decision 主干流程**不动**
- FMU 反欺诈分支、Policy Fail Reject 分支**不动**
- 价格审批、Final Approval、LOU、签约环节**不动**
- CED 现有审核界面框架**不动**（仅加标签和收敛动作）

### 4.3 待决策项（需团队/客户确认）

1. 路径②"带标记进 STP"语义三选一（见 3.1）
2. CED 代处理 OCR 的任务是否计入 CED 工作量考核；是否需要反向激励 Sales（如 CED 协助直通的案件不计入 Sales 的 STP 贡献）
3. pre-check 接口的调用频率与性能预算（实时刷新 vs 手动刷新）
4. "CED 清一项规则后自动批出"是否计入对外 STP 口径

### 4.4 分期落地建议（MVP 优先）

| 期 | 内容 | 价值 |
|----|------|------|
| P1 | 引擎新增 OCR 完整性规则 + 三路径路由 + CED 任务标签 | 跑通核心闭环，立刻获得干净的统计口径 |
| P2 | pre-check 接口 + Sales 就绪度面板 + 提交确认页 | "利益可见"激励上线，有效提交率开始提升 |
| P3 | 五指标漏斗报表 + 告警规则调优机制 | 数据驱动迭代规则 |

## 五、风险与开放问题

| 风险 | 缓解 |
|------|------|
| Sales 把 CED 当免费 OCR 处理通道（路径④滥用）| 监控 CED 协助直通率；必要时引入考核杠杆（见 4.3-2）|
| 预检与正式提交结果不一致引发 Sales 投诉 | 界面明确区分"材料侧检查"与"提交后征信检查"，不做全量承诺 |
| 告警规则噪音过多导致路径②形同虚设 | 引擎告警穿透率月度复盘，噪音规则降级 |
| CED 清规则循环次数过多（单案反复进出）| 设最大循环次数，超限强制转人工 |
