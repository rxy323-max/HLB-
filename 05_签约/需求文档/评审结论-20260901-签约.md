## 一、核心决策：签约模式切换规则（本次最大变更）

### 1.1 前提
只有**同时具备 E-Acceptance 和 Manual 资格**时才存在"切换"这件事。若只满足 Manual，入口**只显示 Manual**，不显示 E-Acceptance（不是置灰，是不显示，也不存在默认选中）。

### 1.2 切换矩阵

| # | 场景 | 能否切换 | 路径与限制 |
|---|---|---|---|
| 1 | 签约未完成（任意中间状态） | ✅ 双向可切 | Manual→E、E→Manual 均可。E-Acceptance 卡在任何一步（第1次指纹 / RIB 看合同 / 第2次指纹）都能切到 Manual；**即使客户已在 RIB 点了 Submit，只要第2次指纹或 OTP 未成功，仍可切** |
| 2 | Manual 已完成、未提交放款 | ✅ 可切回 E | Sales 在文件中心**删除**已上传的 CRA HP Agreement → 系统重置 acceptance 状态回 Pending → 重新进入选择入口 |
| 3 | 已提交放款 | ❌ 不可切 | 文件已不可删除，切换路径自然关闭 |
| 4 | E-Acceptance 失败达上限被强制转 Manual | ❌ 本轮锁定 | **本轮 acceptance cycle 内不可再选 E-Acceptance**。需后端记录失败次数，刷新页面不能绕过 |
| 5 | 签约已 Complete | ❌ 不可切 | 完成即锁定 |

### 1.3 与原 LOAD$ 做法的差异
原 LOAD$ 是"上传一份 CRA HP Agreement (E-Acceptance) 强制翻转状态"。**本次不采用**——因为新系统 E-Acceptance 文书是自动生成、自动归档的，无需手工上传。改为「删除 Manual 上传件即重置」。

### 1.4 张骏要求
所有"强制从 E 切到 Manual"的场景都要落库记录，不能靠前端控制，刷新后不能重新选 E。

### 1.5 任晓宇要求
把散落在文档各处的切换规则**汇总成一张矩阵表**，从第 6 章**提到文档前面**（放在 3.x 状态模型附近）。

## 二、CLT / Amendment 流程重构

### 2.1 首次签约类型决定后续走法

| 首次签约类型 | CLT 后是否需重签 | 状态变化 | 后续可否换模式 |
|---|---|---|---|
| **E-Acceptance** | 需要（若 CLT 改动涉及签署文书字段） | Acceptance Status → Pending | ✅ 可换成 Manual |
| **Manual** | **不需要重签** | 状态保持 Complete 不变 | ❌ 不可换成 E-Acceptance |

**判断依据**：CLT 修改的字段是否涉及需签署的文书 —— 新车 3 份（HP Agreement、Second Schedule、PDS），二手/翻新车 4 份（+ Appendix 4）。**未涉及则状态不变，一直保持 Complete**。

> 依据：客户 JIRA 单（浩哥确认）"前一次签约是 Manual，CLT 不需要客户重新签约即可提交放款"

### 2.2 CLT 页面入口
首次签约成功后再次进入 Contract 页面，**仍显示 E-Acceptance / Manual 两个卡片**供选择（前提是首次为 E-Acceptance）。选择后再进入对应的 CLT 处理页。

### 2.3 CLT 页面结构（E-Acceptance 分支）

```
┌────────────────────────────────────────┐
│ 上：上一轮签约结论 + E-Acceptance Log   │  ← 可点 Print Log
├────────────────────────────────────────┤
│ 中：CLT 变更摘要（高亮字段预览）        │  ← 类似客户在 e-Tracker 看到的内容
├────────────────────────────────────────┤
│ 下：操作区（两步）                      │
└────────────────────────────────────────┘
底部：无 Cancel / Confirm / Back（最多留一个 Back 回选择入口）
```

### 2.4 ⚠️ 操作按钮由三步合并为两步

**原设计（三个按钮）**：① 同步 e-Tracker/RIB → ② 发短信通知客户 → ③ Refresh 刷新状态

**新设计（两步）**：

| 步骤 | 动作 | 后台逻辑 |
|---|---|---|
| **Step 1** | 一个按钮完成"同步 + 发短信" | 按时序：先同步 e-Tracker，**成功后**再发短信 |
| **Step 2** | Refresh 刷新 | 见 2.4.2 刷新范围 |

#### 2.4.1 失败处理
- e-Tracker 同步失败 → **短信不发**，**不推进到 Step 2、停在 Step 1**，状态不刷新，接口返回错误提示"稍后重试"
- **不记 log**：e-Tracker 同步成功与否既不展示也不记录（张骏："log 太多了"）
- **只记短信**：短信发送状态（成功/失败）要展示

#### 2.4.2 Refresh 的刷新范围
Refresh 不是只刷客户签约进度，而是「**刷新这一屏需要展示的所有内容**」，**包含短信发送状态**。

**进入页面可自动 refresh** —— 不强制要求手动点击，每次进入该界面自动刷新是可接受方案。

#### 2.4.3 Resend 按钮
- 位置：Step 2 区域（与 Refresh 同屏）
- 交互：点击 → 显示 loading → 接口返回成功 → loading 结束 → **自动将所有应展示内容刷新上屏**
- 用途：Step 1 中短信发送失败时的手动补发入口

### 2.5 断点记录（后端）

> 注：断点讨论发生在合并决策之前，合并后逻辑简化如下。

| 已发生的动作 | 下次进入时停留位置 |
|---|---|
| 未点过 Step 1 | Step 1 |
| 已同步 + 已发短信 | Step 2（等待客户确认区） |

**硬性要求**：从"已发短信"到"等待客户确认"之间必须做断点，**不允许回到 Step 1 重新发送**。

### 2.6 ⚠️ 原型中的 e-Tracker 客户视图弹窗 = 演示模拟

任晓宇明确："这个地方其实是一个**模拟**的，我们要看客户的界面做的一个 **demo**，相当于真实的里面是没有东西的。真实的这个地方……**就是个 refresh**"

| 载体 | 处理方式 |
|---|---|
| **原型** | 保留该弹窗，用于向客户演示完整客户旅程 |
| **需求文档** | 该位置**只能写成一个 Refresh 按钮**，不得写成系统需实现的客户端功能 |

### 2.7 CLT 完成后 Log 区显示两条记录
- 第 1 条：首次签约 Log
- 第 2 条：本次 Amendment Log

（任晓宇："出现两次这里面就会有两个 log"）

### 2.6 Manual 分支的 CLT 页面
- 若首次为 Manual：CLT 不需重签，页面**不应出现** e-Tracker 同步/发短信区块
- 只保留文书下载区（下载 → 线下签 → 上传）
- **原型 bug**：Manual 页面下方出现的 "Switch to E-Acceptance" 按钮是多余的，需移除（首次 Manual 后不可切 E）

## 三、⚠️ OTP 归属澄清（原型与文档均需改）

### 3.1 结论：OTP 全流程在 RIB 侧，不在 CrediOS

| 环节 | 归属 |
|---|---|
| 触发 OTP 发送页面 | RIB |
| 客户点 "Receive OTP" | RIB |
| 短信下发 | RIB |
| 输入验证码 | RIB 页面 |
| 验证码校验 | RIB |
| Resend OTP | RIB |

### 3.2 CrediOS 侧的正确表现
第2次生物识别失败 → CrediOS 通知 RIB（接口参数 `iqType = second bmt failed`）→ **CrediOS 页面应显示"前往 RIB 操作页 / 等待 RIB 返回结果"，而不是弹出 OTP 输入框**

### 3.3 🔴 阻塞项：缺接口
**目前没有找到 RIB 通知 CrediOS "OTP 验证成功/失败"的接口。**
- 张骏已在群里问对方，未回复
- 影响：若 RIB 不回传，CrediOS 会一直停在"等待验证"状态卡死
- 对方 IT 可能放假到周四；若来不及，**在交付版本中把该处标黄为 Pending，让客户确认**

### 3.4 触发时机确认
OTP 兜底仅用于**首轮签约的第2次生物识别失败**，不用于 CLT，也不用于第1次身份验证。

## 七、已确认的接口调用链（供文档补充）

| 时机 | 方向 | 接口 | 备注 |
|---|---|---|---|
| 第1次指纹成功后 | CrediOS → RIB | 取 session id / token | 拼接 URL 跳转 RIB 签约页 |
| 客户进入 RIB 页面 | RIB → CrediOS | Application Status Inquiry | 拿订单信息展示（Lending Type、App Ref No 等） |
| 客户查看文书 | RIB → CrediOS | EHPA Attachment Inquiry | 拿待签署文书 |
| 客户点 Submit | RIB → CrediOS | Confirm Acceptance Message | 含 decision 字段：`AC`=接受 / `DC`=拒绝 |
| 第2次指纹成功 | CrediOS → RIB | 同跳转接口，参数变化 | `iqType = 2nd biometric success` |
| 第2次指纹失败/超时 | CrediOS → RIB | 同上 | `iqType = second bmt failed`，RIB 据此展示 OTP 页 |
| OTP 验证结果 | RIB → CrediOS | 🔴 **缺失** | 见 Q1 |

**接口交付策略**：接口规范这次就给，尽量按现有 LOAD$ 接口字段定义，避免对方改动。FSD 先给业务看，科技侧后续再对。
