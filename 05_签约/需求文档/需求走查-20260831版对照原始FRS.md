### P0-1 Defects Attachment 自动上传（原文 HP075 第6章 + Training Deck 2.3）

### P1-5 e-Tracker 接口的 hpAgreementInd 复合状态与四个指示器（原文 HP075 10.2 + 12.1.1）

**原文功能**：`APL_STAT_INQ` 报文新增 `hpAgreementInd` 字段，由四个内部指示器组合推算出 1~6 六个值，决定 e-Tracker 前端展示什么：

| eAcceptance Indicator | 1st Signing Complete | Ready for 2nd Signing | 2nd Signing Complete | hpAgreementInd |
|---|---|---|---|---|
| Y | Y | 空 | 空 | 1 |
| Y | Y | Y | 空 | 2 |
| Y | Y | Y | Y | 3 |
| 空 | Y | 空 | 空 | 4 |
| 空 | Y | Y | 空 | 5 |
| 空 | Y | Y | Y | 6 |

四个指示器的盖章逻辑（`StampEAcceptInd`）中有一条容易漏的：

> **1st Signing Complete 在客户完成第2次生物识别时才盖 Y；若第2次生物识别失败走了 OTP，则在收到 RIB 的 OTP 成功消息时盖 Y。**

也就是说"第一次签署完成"这个标记**不是在第一次生物识别后盖的**，而是整个签约动作闭环后才盖——这与直觉相反，容易实现错。

**新文档现状**：11.1 列了接口清单但没有这个字段逻辑；新的 Mode+Status 状态模型也没有映射到这四个指示器。

**建议**：在接口章节补充该字段的取值矩阵，并明确新状态模型与四个指示器的映射关系（否则 e-Tracker 侧无法正确展示进度）。

### P1-6 生物识别准入矩阵的可配置性与 Owner 角色（原文 HP047 第5章）

**原文功能**：两张**可配置矩阵**，维度为 `客户类型 × BNM Group Code × 与申请的关系 × 证件类型`：

- `BIOMETRIC_CRITERIA_CHECK`：决定该人是否**需要**做生物识别
- `BIOMETRIC_MANDATORY_CHECK`：决定不做完是否**卡流程**

关键点：关系维度是 **Primary Applicant / Guarantor / Owner** 三个角色，不是两个。原文矩阵中，**Corporate 类客户的 Owner（车主）角色需要做生物识别 = YES**（Commercial Bank、Company、Partnership 等各类 BNM Group Code 下，Owner 列均为 YES）。

**新文档现状**：客群分流表只覆盖"主申请人 + 担保人"，**Owner 角色完全没有出现**；TABLE 6 里 Non-Individual 直接写"纸质上传/无 Biometric"，与原文 Corporate Owner 需要生物识别的规则冲突。另外两张矩阵"可配置"这一属性也没写。

**建议**：确认 Owner 角色在新系统中是否保留（若车辆登记人与借款人不同则需要）；补充矩阵可配置性要求。

## 四、P2 — 细节补强

### P2-1 卖家（Seller Direct）的生物识别
原文 HP047：Biometric 搜索页列出的是"所有申请人**及卖家(Direct)**"，由 `BIOMETRIC_CHECK_SELLER` 开关控制（I/C/OFF），且**一旦开启即为强制完成项**。新文档全篇未提卖家作为生物识别对象。（注：你早前给我的客户反馈第4类"受后台开关控制的选做项"应该就是指这个，但没写进文档。）

### P2-2 应用内 Biometric Tab（原文 HP047 4.4）
除了独立的 Biometric 详情页，原文还要求在**申请详情页内**有一个 Biometric Tab，支持多申请人记录切换（Select 单选 + Applicant Type + ID No + Name），下方展示该人的扫描详情，含 Remarks / Report / Save 按钮。特别注明：**Save 按钮的权限只开放给 Letter Printing 步骤的 Sales**，供其补填 Remarks。新文档 8.1.5 只写了入口位置，没有这个多人切换的 Tab 结构。

### P2-3 设备错误码映射表（原文 HP047 附录2）
原文提供 SmarTec 与 Sagem 两款设备的完整错误码 → LOAD$ 状态码映射（`0`=Matched、`-1`=读卡失败、`-2`=指纹验证失败/超时、`-3`=模板无效、`-4`=Unmatched、`-5`=设备序列号无效）。新文档 8.1.2 只列了设备型号，Step 3 的状态提示文案覆盖了部分场景但不系统。建议以附录形式收录，供开发对接设备 SDK 时使用。

### P2-4 Biometric 独立菜单位置（客户反馈第2条，原文 HP047 第4.1节）
原文明确 Biometric Scanning 是**独立菜单项**（`The biometric screen will be made available under the following menu`，并注明适用用户权限矩阵）。客户反馈进一步指定放在 **e-Hakmilik 之上**。新文档把生物识别完全描述为签约流程内的步骤，没有独立入口的位置说明。

### P2-5 放款流程与自动挂载文件清单（Training Deck p.6–7）
原文明确电子签案件**自动挂载 5 类文件**：HP Agreement、Second Schedule Part 1、Product Disclosure Sheet、**Customer Biometric Scanning Result**、Appendix 4（二手/翻新车）。且明确"客户生物识别结果单**不需要**作为放款文件单独提交，系统自动挂载"。

放款推进步骤：`Proceed with E-Acceptance` → 案件从 Letter Printing 流到 Pending Funding Document，状态 Approved → **Accepted** → 补齐剩余放款文件 → `Route to CRA checker`。若必填文件未挂齐，系统报错拦截。

新文档 10.4 列了 4 类文件（漏 Biometric Result），TABLE 18 的"后续步骤"只写了"proceed to CRA"，缺状态从 Approved 变 Accepted 这个关键状态跃迁。

### C-2 术语表与正文对 Hybrid 的归属矛盾

- 1.1.2 术语表：`电子签约（混合）| E-Acceptance(Hybrid) | 流程 | Biometric Verification+Paper Signing`
- 第5章标题与 TABLE 5/7：均改称 `Manual Acceptance (Hybrid)`

两处名称不一致。原始 FRS 用的是 `E-Acceptance (Hybrid)`。**建议统一**——考虑到 Hybrid 实际不发生任何电子签署动作，划归 Manual 层级在业务上更准确，但需要同步修订术语表，并在文档开头注明"本次相对原 FRS 的归类调整"，避免客户对照原文时困惑。

### C-3 指纹重试次数在四处取值不一致

| 位置 | 写法 |

| TABLE 13（Step3 失败后续） | `允许重试（≤999次）；累计失败达3次上限→转Manual` |
| TABLE 19（异常A） | `累计失败次数<Attempt Counter配置值 \| 允许继续尝试（最多≤999次）` |
| TABLE 45（General Constant） | `Attempt Counter \| 3次（可配置，最大999）` |
| TABLE 69（A-1） | `允许重试（≤999次）` |

同一份文档内 3 次和 999 次并存，TABLE 13 甚至同句自相矛盾。**建议统一表述为**：`默认3次，通过 BIOMETRIC_ATTEMPT_COUNTER 配置，系统上限999`。

### C-4 章节编号重复

- 目录中 `12.客户通知与状态查询` 与 `12.异常分支汇总` 编号重复（应为 12 和 13）
- `13.待客户确认项` 相应顺延为 14
- 正文 `11.2.5 General Constant（e-Tracker）` 实际嵌套在 12.2 e-Tracker客户端 之下，编号与层级不符（应为 12.2.5）
- 第9章标题为 `9. 签约日志与报告输出`，第10章为 `10．报表与文档归档`，两章内容有重叠（Print Log 在 9.3，Biometric Report 在 10.1），建议合并或明确分工边界

### C-5 状态模型中 Fail 的处理有设计风险

3.1 设计说明：`Fail不再作为独立状态，而是 E-Acceptance Mode+Pending Status 下的异常标记`。

但 TABLE 11（列表页展示规则）**没有为失败场景保留展示行**——按该表，失败案件和正常进行中案件在列表页均显示 `E-Acceptance:Pending`，无法区分。

原文 Fail 状态的业务语义是"**客户已经尝试过但失败了，必须转手动**"，对 CRA 和主管而言这是需要介入的信号，与"客户还没开始"是完全不同的处理优先级。

**建议**：要么列表页增加失败标识（如 `E-Acceptance:Pending (Failed)`），要么保留 Fail 作为可展示值。当前设计会导致运营侧丢失一个关键的分拣维度。

### C-6 Print Log 字段设计与原文差异较大

| | 原文 Print Log | 新文档 TABLE 52/53 |
|---|---|---|
| Header | Name、**Relationship to Application**、App.Ref.No、**Bank Name**、**Lending Type**、Loan Account No（6字段） | Application Reference No.、Customer Name、ID No.、Acceptance Mode、Acceptance Status、Generated Date、Generated By、Page Count（8字段） |
| 明细 | E-Acceptance Type、**PDS(Y/Blank)**、**Second Schedule(Y/Blank)**、**HP Agreement&T&C(Y/Blank)**、**Appendix4(Y/Blank)**、Status、DateTime、Remark（8列） | Document Name、Document Type、Version、Signed By、Signing Method、Signing Date、Biometric Result、OTP Result、Archiving Status（9列） |

新版本从"按签约动作看每份文件是否已接受"改成了"按文档看签署详情"。新设计信息更丰富，但**丢掉了原文最核心的四个 Y/Blank 标记**——这四列是审计时快速核对"这一轮签约客户到底接受了哪几份文件"的依据，也是 Bank Acceptance 行与 Hirer 行的区分方式（银行只签 SS 和 HPA，不签 PDS）。

另外原文的 **Bank Name 取值规则**未被继承：`Lending Type = Conventional → 显示 'Hong Leong Bank Berhad'；Islamic → 显示 'Hong Leong Islamic Bank'`。

**建议**：保留原文四列 Y/Blank 标记，与新增字段并存；补充 Bank Name 取值规则。
